# RECONCILIATION — 一页提案格式契约

> **依据**：`governance/C0_MoHen_Project_Constitution_and_Dual_Line_Collaboration_V1.0.md` §6.2（保留 Architecture Reconciliation）+ §7（越界升级）。
> **为什么要有这份契约**：C0/C1 定义了"什么必须提交拥有者确认"，但**没有规定提案长什么样**。结果每个 AI 交上来的东西形状各异（三个方案 / 十页分析 / 一句"建议走 Reconciliation"），拥有者无法横向比较，也**无法判断这是真需要他，还是 AI 在拿这个词当挡箭牌**。
> **校验**：`pnpm guard:reconciliation`（`scripts/check-reconciliation.mjs`）。写得不合规的提案 → 守卫红。

## 1. 一页，五项，缺一不可

提案必须**一页以内**，且具备下列五项（标题须逐字一致）：

| 项 | 标题（逐字） | 必须回答 | 合格的样子 |
|---|---|---|---|
| 1 | `## 改什么` | 具体改哪个对象 / 字段 / 契约；**并写明不改什么**（边界声明） | "给 `visual_assets` 增一个正面资格字段；**不改** `eligibility_tags` 的含义" |
| 2 | `## 为什么` | 触发它的**证据**（可核查的事实，不是推测）；以及**不改的代价** | "实测 1246 张图在无描述、无门禁记录时被视为可用" |
| 3 | `## 影响谁` | 受影响的表 / 契约 / 体验 / 代码路径；谁会**被迫改变行为** | "`effective_visual_assets` 视图过滤条件变化 → 8 条有效资产口径随之改变" |
| 4 | `## 怎么回滚` | 如何撤销；能否分步；**哪些部分不可回滚** | "新字段可 DROP；已置为 gate_passed 的行需按批次还原" |
| 5 | `## 请你回答什么` | **可以回答的具体问题**，最好给选项 | "选 A / B / C？" |

## 2. 反挡箭牌条款（本契约的重点）

> **第五项必须写出可以回答的具体问题。若写不出具体问题，该提案不合格 —— 说明这一步本可以自主完成，不应提交。**

**理由**：与"禁止写『待查』"是同一条纪律。『建议走 Architecture Reconciliation』如果不附具体问题，就是把「我该判断」包装成「等你判断」，然后把事情无限期停在你桌上。

## 2.5 自足性：拥有者读完这一页就能回答

> **提案必须自足 —— 拥有者不需要去别处找记录，不需要先学术语，就能回答。**
> 2026-10-02 首个实例（RECON-01）违反了本条：它把三个方案压缩成脚注、用未解释的术语提问，导致拥有者**六个问题一个也答不上**。**格式对、实质不可答，等于没提。**

四条硬要求：

1. **每个术语在提案内必须有一句解释。** 不得出现"见某文件"式的悬空术语（如直接问"要不要置为 rejected"而不说 rejected 是什么）。
2. **每条问题必须写出"选它的后果"**，格式：问题行下面紧接一行以 `→` 开头的后果说明（多个选项就写多行 `→`）。
3. **凡问句提到「方案 A / B / C」，正文必须先有该方案的定义块**（`**方案 A**` …），且写明"选它的代价"。
4. **能由开发平台自己查清或判断的，不许变成问句。** 技术性前置检查、分步实施顺序、回滚方式——这些属工程判断，写进 `## 我已查清（不需要你回答）`，不要占用拥有者的问题额度。

**可选第六节**：`## 我已查清（不需要你回答）` —— 主动列出"我替你做掉的判断"，让拥有者看到还剩下什么是真需要他的。

> **守卫能做到什么、做不到什么（诚实说明）**
> `pnpm guard:reconciliation` 能拦：缺项、空章节、问句无问号、问句下无后果、**提到方案却无定义块**、
> 状态已裁定却无裁定结果。
> **它拦不住**：定义写得含糊、后果写得像套话、问题虽然"可回答"但问错了层级（把工程判断推给拥有者）。
> 这几项**只能靠人判断** —— 反过来说，拥有者若觉得"这问题我不该被问"，**那就是提案不合格**，
> 直接退回即可（这比让守卫猜更可靠）。
>
> **补充陷阱（2026-10-02 实测）**：判断"有没有定义块"时，若在**整篇文件**里做字符串匹配，
> 问句**自己就会满足它**；改成"问句之前"后，又会被正文里的**行内提及**满足。
> 故规则收紧为：**定义块必须另起一行**（`^**方案 X**`）。

## 3. 头部四行（机器可读，供守卫定位）

提案正文之前必须有：

```
> **提案类型：Architecture Reconciliation**
> **提案编号**：RECON-<编号>
> **日期**：YYYY-MM-DD
> **状态**：待裁决 ｜ 已裁定
> **涉及层级**：C0 / C1 / C2 / C3 / C4（可多选）
```

- 第 1 行是**标记**：守卫据此识别哪些文件是提案（无需维护清单，也无需人记得登记）。
- 第 4 行只允许两个值：`待裁决` ｜ `已裁定`。**已裁定的提案必须补一行 `> **裁定结果**：…`**，否则守卫红（避免"批了但没写结论"）。

## 4. 模板（复制即用）

```markdown
> **提案类型：Architecture Reconciliation**
> **提案编号**：RECON-0xx
> **日期**：YYYY-MM-DD
> **状态**：待裁决
> **涉及层级**：C3

## 改什么
（具体对象 / 字段 / 契约；并写明**不改什么**）

## 为什么
（可核查的证据；不改的代价）

## 影响谁
（表 / 契约 / 体验 / 代码路径；谁被迫改变行为）

## 怎么回滚
（撤销方式；可否分步；不可回滚的部分）

## 请你回答什么
1. …？（选项 A / B / C）
```

## 5. 不合格的常见形态（守卫会拦）

| 形态 | 为什么不合格 |
|---|---|
| 只有"建议走 Architecture Reconciliation" | 缺五项；且没有具体问题 |
| 第五项写"请确认" | 不是可回答的具体问题 |
| 第五项写"是否需要进一步评估？" | 把决定权推回给拥有者，等于没提案 |
| 状态标"待裁决"但没有明确问题 | 拥有者无从下手 |
| 状态标"已裁定"但没有裁定结果行 | 结论丢失 |
