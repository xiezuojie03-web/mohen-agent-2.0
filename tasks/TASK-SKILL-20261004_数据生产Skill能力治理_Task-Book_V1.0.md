## 1. 背景与目标

**项目目标（拥有者 2026-10-04）**：把**数据底座建厚实**——可信一手数据的来源与规模做厚做实。路径：先深透老项目（沪上经纬），再持续推进外部扩源（`C0` §11 R18–R20）。

**本任务解决的真问题（拥有者原话）**：「避免每次数据生产都要重新写脚本，最后是一大堆重复的脚本。」

**手段**：把数据生产从「一次性手工脚本」变成**可复用、可扩展的 Skill 能力**。本任务是**后续规模化外部扩源的必要基建**——先让"能力"沉淀成技能与脚本，再让扩源跑在可复用的流水线上，而不是边扩边堆重复脚本。

---

## 2. 现状（白话诊断，2026-10-04 调研）

数据生产已有一套像样的机制（双模式、证据门禁、研究工作区、十几道机器校验），但这些能力**没有变成"能反复用的工具"**。三样东西各干各的、互不连通：

| 三方 | 现状 | 缺什么 |
|---|---|---|
| **技能说明书** `skills/` | 10 个 `SKILL.md`，**只有文字描述**，没跟干活脚本连起来 | 实体化（固定入口 + 契约 + 登记） |
| **干活的脚本** | ~110 个 `.mjs`，散在 `pipelines/` `scripts/` `tools/` **根目录** | 归属与去重 |
| **作业清单** `specs/data-production/production-registry.json` | 登记数据作业，但**无 `implementation` 字段**（不写靠哪个技能/脚本） | 作业↔实现的对照 |

**病根一句话**：**技能 ↔ 脚本 ↔ 作业三者无三向索引**，所以既没法复用、没法查重、也没法交接。

**机器已经抓到的证据**：
- `check-structure-map` 报**根目录 14 个未登记 `_*.mjs`**（`_probe*.mjs` / `_v2/_v3/_v4.mjs` / `_rebuild/_unlock/_verify/_schema/_full.mjs` …），且与 `tools/production/probe-*.mjs` 功能重叠。
- **5 类功能重复**：① 库探针（根目录 vs `tools/production`）；② 空间对齐三胞胎（`pipelines/historical-spatial/probe-align-{entities,extra,final}.mjs`）；③ e2e 脚手架 ×5（`scripts/e2e-*-capture.mjs` 共用同一套 helper）；④ 去重双轨（查 `check-evidence-dupes` / 清 `cleanup-dupe-evidence`）；⑤ evidence 恢复双轨（`recover.mjs` vs `repair-polluted-runs.mjs` / `db-dedup-gate-audit.mjs`）。

---

## 3. 理由（为什么现在治）

1. **外部扩源任务量大**——若不先沉淀能力，每次扩源都堆重复脚本，底座越厚越难维护、无法交接。
2. **C2 双 Skill 架构早已定义 Skill**（`C2` §2 / §3.1 / §9.1），但**一直只停在文字，没落地成能调用的实体**。
3. 宪法已要求"能力实体化 / 复用 / 门禁"，但**缺"单一实现、禁止平行重复"的强制**——所以"每次重写脚本"一直没人管。

---

## 4. 目标（做完长什么样）

1. 每个数据生产能力 = 一个**真技能**：`SKILL.md` + 固定入口 entry + 输入输出契约 + 在清单登记 `implementation`。
2. **技能 ↔ 入口 ↔ 作业三向可查**（守卫强制）。
3. **重复脚本收敛**：根目录 14 个 `_*.mjs` + 5 类重复处理完，`check-structure-map` 未登记根条目 = 0。
4. **"先查技能再写脚本"成硬规矩**，防"治好了又复发"。

---

## 5. 四步计划

> 每步：产出 / 验证 / 回滚。全部只改契约·登记·文档 + 少量脚本重构；不动数据库与数据；不自动晋级（R15 门禁不变）。

### 第 0 步 · C2 宪法基线（前置 · 已完成 · 决断 R26）
- **产出**：C2 增补 **§2.1 Skill 实体化与复用铁律**（实体化判定四条 + 唯一权威实现 + 复用优先/禁止平行重复 + 三向绑定）、**§3.1** 唯一权威实现注记、**§9** 重复即合并、**§9.1** 最小合同扩为含 Implementation / Reuse Source / Merge·Deprecate。已登记 `C0` §11 **R26**。
- **为什么前置**：C2 是"规则"，四步是"执行规则"；规则先立，四步才有宪法依据。
- **验证**：C2 内容增补（文件不改名，维持 V1.1；正式升版另议）。

### 第 1 步 · 作业清单加「实现」字段（地基 · 风险最低）
- **产出**：`production-registry.json` 每个 job 增 `implementation: { skill, entry }`（14 作业全覆盖，schema_version 1→2，required_fields 增 implementation）；扩 `check-production-registry.mjs` 第 ⑧ 项校验——① `implementation` 必填且为对象；② `entry` 必须是真实存在的脚本；③ `skill` 必须在已知技能集合（`skills/` 目录 ∪ C2 §3.1 候选）；④ **每个技能唯一权威 entry**（同一 skill 的所有作业必须声明同一 entry，违反即红——对应 C2 §2.1「禁止平行重复实现」）。
- **设计修正**：原设想「一个 entry 不得被多 job 声明」**已纠正**——`unattended-runner.mjs` 是单体 runner，合法服务多个作业；真正的去重规则是「每个技能一个权威 entry」。
- **验证**：`pnpm guard:registry` 绿；**反证 4 类违规均会红**（entry 不存在 / 未知 skill / 同 skill 多 entry / 缺 implementation），注册表已还原干净。
- **回滚**：字段与守卫独立提交。

### 第 2 步 · 技能说明书升级为「真技能」
- **产出**：10 个 `SKILL.md` 补 `entry`（入口命令）、`input/output` 契约、对应 job、实现脚本、来源指针；扩 `check-structure.mjs`——每个 skill 必须声明 entry 且能在 registry 找到对应 job（`SKILL_FLOOR` 保持）。
- **验证**：`pnpm guard:structure` 绿。
- **回滚**：`SKILL.md` 逐个可回。

### 第 3 步 · 收敛重复脚本（**R14 归档不删除** · 拥有者 2026-10-04 确认）
- **产出**：根目录 14 个 `_*.mjs`——能并入现有技能的并入；纯临时的移入 `archive/` 并在 `OWNERSHIP_MAP` 登记（**R14 归档不删除，保留可追溯**）。5 类重复抽公共模块（库探针复用 `tools/production`；空间对齐三胞胎→1 个可参数化；e2e→共用 helper；去重/恢复双轨→抽共享）。
- **验证**：`pnpm guard:structure` + `guard:registry` + `guard:links` 绿；`check-structure-map` 未登记根条目 = 0；功能不回归（`pnpm test` / `test-isolated`）。
- **回滚**：每组独立提交，归档可回迁。

### 第 4 步 · 立「先查技能再写脚本」硬规矩

**新增任何数据生产脚本前，必须走这四步（缺一不可）**：
1. **先查** `specs/data-production/production-registry.json`——该能力是否已有作业？其 `implementation.entry` 是什么？
2. **再查** `skills/<name>/SKILL.md` 的「实体化档案」——是否已有可复用的 Skill 与 Entry？
3. **能复用就复用**：在既有 Entry 上加参数 / 加作业，**不新建脚本**。
4. **确属全新能力**：新建 Skill（`skills/<name>/SKILL.md` 含 §9.1 最小合同 ＋ 实体化档案）＋ 在注册表登记作业与 `implementation`（skill ＋ entry），并同步 `OWNERSHIP_MAP`；**禁止**在仓库根目录留一次性脚本。

**机器强制（已落地，不依赖自觉）**：
- `guard:registry`（第 ⑧ 项）：每个作业必须有 `implementation.{skill, entry}`；entry 真实存在；skill 在已知集合；**每个技能唯一权威 entry**（平行重复实现会红）。
- `guard:structure`（绑定校验）：注册表挂了作业的技能必须有 `SKILL.md`，且其 `Entry` 与注册表一致（防未落地 / 文档漂移）。
- `guard:structure-map`：**根目录任何新 `.mjs` 都会因未登记而红**——这就是"不许散落脚本"的机器闸门。
- **反证**：故意在根目录丢一个脚本 → `UNDECLARED_ROOT_ENTRIES` 会红（exit 1）；移除后恢复 `undeclared=0`。

## 6. C2 优化（**已完成 · 第 0 步 · 决断 R26**）

**评估结论**：C2 的 Skill 章节（§2 定义 / §3.1 家族表 / §9 成熟晋升 / §9.1 最小合同）概念完整，但缺三条规范性强制，正是它们导致"Skill 只停文字、每次重写脚本"：
1. 缺**实体化判定**——没定义"一个 Skill 算不算真落地"（应 = SKILL.md + 固定 entry + 契约 + 在 production-registry 登记 `implementation`）。
2. 缺**单一实现 / 复用优先**铁律——没规定"每个能力一个权威实现（canonical entry），新增脚本前先查复用，平行重复实现属违规"。
3. 缺**三向绑定 + 合并/废弃**——没要求技能↔入口↔作业互相可查，也没说重复时合并、废弃时按 R14 归档。

**已落地（拥有者 2026-10-04 授权修改 C2）**：
- `C2` **§2.1（新增，冻结）**：Skill 实体化判定四条 + 唯一权威实现（canonical entry）+ 复用优先/禁止平行重复 + 三向绑定；未登记且不属于任何 Skill 的新脚本不允许合入。
- `C2` **§3.1**：增补「每个 Skill 对应唯一权威实现；新增实现前先查复用；平行实现按 §2.1 收敛」。
- `C2` **§9**：增补「重复即合并」（不新增第三个、也不并存，收敛为唯一权威实现，其余 R14 归档）。
- `C2` **§9.1**：最小合同扩为含 **Implementation**（三向绑定）/ **Reuse Source**（复用来源）/ **Merge·Deprecate**（合并·归档去向）。
- 登记于 `C0` §11 **R26**。**版本源唯一**（C0 §10）：本次内容增补、文件不改名，C2 维持 V1.1（各节标注日期）；正式升版另议。

> **机制落地不在 C2**，放 `production-registry.json` / `skills/` / 守卫——即下面第 1–4 步。

## 7. 「四步能否实现数据底座建厚实」诚实判断（拥有者 2026-10-04 提问）

**结论：四步本身不直接产数据，它是"使能器"；底座建厚实 = 四步（基建）+ 实际数据扩展（老项目深透 + 外部扩源）两者配合。**

- 四步解决的是**机制可持续性**——让数据生产变成可复用流水线，从而后续扩源能规模化、不重复。这直接服务你的目标，也是扩源的**必要前置**。
- 但「底座建厚实」= 真正把可信一手数据（家谱 / 地方志原文 / 历史图片 + 外部多源）**挖进来、变多变可信**——这要靠**实际跑数据生产**，四步不产任何数据。
- **为什么仍建议先做四步**：若先扩源、后治理，边扩边堆重复脚本，底座越厚越难维护；先修机器、再用修好的机器扩源，才可持续。
- **两条线并行**：① skill 治理（本任务书，修机器）；② 数据扩展（老项目深透 + 外部扩源，产数据）。四步让②跑在可复用流水线上。
