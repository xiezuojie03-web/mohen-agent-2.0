# CEI E步｜Studio与Admin专项评估（现行）

> 执行依据：CEI-01_Taskbook.md V4.1 §3.5.5 E；对照MHKA-01—05中直接影响产品体验的合同，重点核对MHKA-02 §3、§6、§12。性质：产品设计质量审查，不是GitHub UI继承审查、工程审计或实施授权。
> 当前裁决：E_STUDIO_ADMIN_REVIEW_COMPLETE / TARGETED_REDESIGN_RECOMMENDED / OWNER_REVIEW_PENDING / F_PERSONAL_SPACE_REVIEW_NEXT / NO_GITHUB_INHERITANCE_REVIEW / NO_ENGINEERING_AUTHORIZATION。

## 1｜核心结论

**当前Studio/Admin原型已经把部分业务责任和状态边界表达出来，但还不足以证明创作者获得了顺畅、Agent主导的研究创作体验，也没有呈现Admin作为完整运营编辑部与知识资产治理工作面的设计。建议定向深化，不推倒重做。**

- Studio的三工作面桌面结构可保留；研究任务、候选知识、独立资格、作品修订和发布申请也已在语义上分开。当前最大问题不是缺少按钮，而是Agent的真实工作过程没有被表达，创作者仍需手动推进内部流程。
- Admin把作品Reviewer、专业G5、媒体权利和Operator发布分开，是正确的责任设计；但现有原型主要是单一作品修订的审核/发布模拟，缺少知识资产治理和用户/平台治理两个必要业务域。
- **用户管理应属于Admin治理范围，但不应变成新的一级产品模式，也不应与“我的墨痕”个人空间混同。** Admin负责平台级账户、角色、权限、贡献治理、安全与审计；“我的墨痕”负责用户自己的记录、收藏、项目、贡献状态与隐私设置。

## 2｜审查范围与证据

### 2.1 设计合同

- MHKA-02 §3：Studio目标是创作者对话即可委托一份真正逐步形成的历史人文作品；宽屏为左侧自然语言委托、中间Agent研究进展与导演谱、右侧实时作品舞台；窄屏按三个工作区切换，不得简单堆叠或压缩三个等宽栏。
- MHKA-02 §3：研究与作品应双产出；材料、研究候选、正式D/L/G资产、节目/作品修订、审核/公开指针等身份分开；Agent应真实理解委托并组织研究，不能只返回研究计划模板。
- MHKA-02 §6：Admin是授权管理工作面，包含作品审核、驳回、返工、版本比较、合法发布/撤回、公开目录、运营指标、知识资产检索、许可/依赖/失效信息、模型成本与任务状态。
- MHKA-02 §6：知识资产管理至少应让Owner查看具体条目的来源/读取/证据、时地、认识状态、关联、当下生活价值、权利/资格、版本、研究使用、内外贡献和补证缺口；可检索、查看细节、追溯来源，并对确需Owner决定的问题采取行动。

## 3｜Studio：创作者完整任务审查

### 3.3 Studio应保留的部分

- 桌面三工作面分工：左侧委托/对话，中间研究进展与证据，右侧作品舞台。
- 研究候选、正式资格、作品修订、发布申请分账；研究完成不等于知识合格，保存不等于发布。
- 对缺少来源、未绑定原件、资格HOLD、接口失败和重复提交给出明确阻断，不制造成功幻觉。
- 保留既有项目、研究台、A/B导演、不可变修订和提交申请，不重建第二套Studio。

### 3.4 Studio定向深化方向

创作者只需要表达目标、回答必要澄清、选择方法/方向、确认关键事实与授权、修改作品和决定是否提交。墨痕负责理解与拆解任务、推荐研究路径、组织来源与证据、发现缺口、协调受控生产、形成可检查研究成果、提出导演方案并协助局部修改。D/L/G是后台专业生产和资格合同，不应成为创作者必须学习的操作菜单；必要时可在“专业依据/详细状态”中查看。

## 4｜Admin：知识资产治理与用户/平台治理

### 4.1 当前Admin原型实际覆盖

当前Admin原型有五个演练工作区：总览与下一步、独立作品签核、运营待办、发布与撤回、资格与负例。它清楚区分Reviewer、Operator、专业G5、媒体权利和发布动作；无待办时显示空态，缺少签核/G5/权利/当前修订时阻止发布。UI-A 108/108和UI-C 62/62历史测试为这些模拟角色、修订和阻断路径提供了局部证据。

但当前Admin原型的主要对象是一份作品修订及其发布资格；HTML中没有知识资产目录/详情工作区，也没有用户管理入口。角色切换按钮只是模拟身份，不是账户、角色或权限管理。这里存在一项明确的设计表达缺口：CEI-4-5规格§4.2.2已要求保留知识资产与用户管理入口，但当前统一HTML的Admin五个局部导航点没有呈现这两个域。本轮只判断CEI设计表达，不据此推断GitHub既有Admin代码是否已有相应功能；后者属于第二轮继承审查。

### 4.2 缺陷与治理判断

| ID | 严重度 | 问题与证据 | 修复目标与关闭条件 |
|---|---|---|---|
| E-ADMIN-01 | P1 | **知识资产治理视图缺失。** 现有五个工作区围绕作品签核和出版，无法按具体知识条目查看来源/读取/证据、时地、认识状态、关系、当下生活价值、资格/权利、版本、研究使用、贡献和补证缺口。 | 在Admin内增加知识资产治理工作区：可检索的资产清单与状态筛选；单条资产详情/来源链/主张证据/关系/时地/资格/权利/版本/使用/贡献/缺口；显示需要Owner或专业角色决策的事项。不要用G5数量、KPI或SQL字段替代具体资产可读性。 |
| E-ADMIN-02 | P1 | **用户与平台治理视图缺失。** 当前原型没有账户、角色权限、贡献、异常、隐私、安全和审计工作区。V4.1 §3.5.5 E明确要求Admin审查这类治理，并将用户管理归入Admin。 | 在Admin内增加用户/平台治理子域：账户状态、角色与资源/项目/动作权限、贡献与授权记录、异常行为、隐私请求、安全事件和审计追踪；按最小权限显示，敏感查看/修改均留审计。 |
| E-ADMIN-03 | P2 | **作品治理与知识治理容易被一个“审核”概念混淆。** 当前原型能区分作品Reviewer与G5，但未呈现知识资产的专业审查、权利核查、运营发布之间的对象和回执关系。 | 知识资产治理、专业Gate、媒体权利、作品Reviewer和Operator发布分别显示对象、责任人、状态、依据和下一动作；Admin不得代签专业Gate，Reviewer不得代替Operator发布。 |
| E-ADMIN-04 | P2 | **总览更像单作品流程卡，不是多任务运营工作面。** 当前总览以一个测试修订和少量计数展示状态；缺少知识缺口、待补证、失权依赖、用户治理异常和任务运行等跨域待办。 | 总览只做“下一步与风险汇总”，按角色显示真正需要处理的事项；点击进入具体资产/作品/用户记录。无可核数据时明确空态，不展示虚构KPI。 |

### 4.3 用户管理是否应纳入Admin

**结论：应纳入，但作为Admin内部的平台治理工作区，而不是新增一级产品模式。**

| Admin用户治理 | “我的墨痕”个人空间 |
|---|---|
| 管理账户状态、角色、资源/项目/动作权限与授权范围 | 用户查看和管理自己的账户资料、隐私偏好与个人记录 |
| 查看贡献提交、授权状态、处理回执及审计 | 用户查看自己的贡献记录、提交状态和撤回入口 |
| 处理异常行为、滥用、权限异常、安全事件和隐私请求 | 用户管理自己的收藏、探索轨迹、创作项目和观看记录 |
| 对敏感操作执行最小权限、双人复核/留痕和数据访问审计 | 用户控制个人数据的保存、分享、导出、撤回或删除 |

Admin不应成为社交CRM或社区后台，也不应让管理员默认浏览所有用户的私人内容。对私有项目、个人记录和敏感信息的查看必须有明确业务理由、最小权限和审计记录。知识资产管理也不应另建独立平台：它是F05 Admin内部的核心业务域。

### 4.4 Admin建议的信息结构

1. **知识资产治理**：资产清单/检索→单条详情→来源与证据链→关系及时空→资格与权利→版本与使用→贡献和缺口→需决策事项。
2. **作品审核与发布**：Reviewer作品签核→专业G资格与媒体权利复核→Operator发布/撤回→WATCH当前合法消费状态。
3. **用户与平台治理**：账户/角色/权限→贡献与授权→异常/安全/隐私→审计。
4. **生产与运营观察**：研究任务、Agent/模型运行、失败和成本等运营状态；仅显示角色有权查看且可核实的数据。

以上均为Admin内部工作区，不新增顶层导航或独立知识资产平台；首页仪表板仅汇总风险与下一步，不替代资产和用户的逐项治理。

## 5｜跨工作面与证据边界

- Studio→Admin→WATCH的模拟身份、作品修订和发布状态交接有历史UI-C 62/62证据，说明设计夹具中的R1/R2身份同步问题已被定向修复；这不是服务端持久化或真实发布证明。
- UI-A 108/108证明角色边界和发布负例的局部原型行为；它没有覆盖知识资产目录、用户管理或真实平台治理。
- UI-B 87/87证明三工作面模拟路径和阻断逻辑；其移动端“三区仍显示”断言不足以证明窄屏工作区切换要求。
