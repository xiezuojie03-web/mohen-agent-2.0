# RECON-02 · 宪法名与真库名分叉：一个分叉，四件事

## 改什么

**现状**：宪法用**单数名**，真库用**复数＋领域前缀**。按宪法名找表会得到"表不存在"。

| 概念名（宪法） | 物理名（真库） |
|---|---|
| `entity` / `visual_asset` / `source_record` | `entities` / `visual_assets` / `source_records` |
| `event` / `change` / `meaning_candidate` | `cultural_events` / `historical_change_records` / `cultural_meaning_candidates` |
| `human_review` / `claim_evidence_link` | `human_review_decisions` / `claim_evidence` |

**但实测发现：这不是一个分叉，是四件事。只有前两件是"命名"。**

| 类别 | 例子 | 是命名问题吗 |
|---|---|---|
| **甲** 纯复数 / 缩写差 | `entity`→`entities`、`ingestion_run`→`ingest_runs` | **是** |
| **乙** 加领域前缀 | `event`→`cultural_events`、`change`→`historical_change_records` | **是**（前缀还能防泛名） |
| **丙** 改名 / 去后缀 | `claim_evidence_link`→`claim_evidence`、`human_review`→`human_review_decisions` | **是**（语义微调） |
| **丁 结构分裂** | `historical_space_claim` → **拆成 5 张表**；`relation_claim` → **双存储并存** | **不是** —— 改名解决不了 |

另有**真库有、宪法未逐条列**的 8 张：`claims`、`evidence`、`relations`、`relation_evidence`、`evidence_gate_audit`、`review_queue`、`knowledge_paths`、`knowledge_path_steps`、`legacy_mappings`。

三种做法：

**方案 A**（建议）：**把"概念名 ≠ 物理名"固定成设计**，而不是消灭它。
- ① 在 C3 写明：**宪法正文一律用概念名**（单数，如 `entity` / `visual_asset`）；**物理表名以真库为准，不在宪法里逐条硬写**。
- ② 建一份**唯一映射**（概念名 → 物理落点 + 状态：已建 / 拆分 / 双存储 / 延后 / 未建），放进 `specs/DATA_CONTRACT.md`（该文件**已批准改造为机器可读契约**，本段正好是它内容的第一部分）。
- ③ 加守卫：真库每张表**必须被映射登记或有显式豁免**；映射里写的物理名**必须真的存在**。
- **不改任何表名、不迁移、不动数据。**

**方案 B**：**以宪法为准重命名表**，做到完全一致（`entities` → `entity` 等）。
- 代价：改 **28 张表里的约 20 张**，连带**全部外键、视图、4 个触发器、20 余个脚本里的 SQL**，并迁移既有数据。收益是"名字完全一致"。

**方案 C**：什么都不做，只在 `CURRENT.md` 记为已知风险。
- 代价：**"按宪法名查表 → 表不存在"的误判会继续发生**；每加一张新表都可能新增一处分叉。

## 为什么

实测（2026-10-02）：

| 事实 | 实测值 |
|---|---|
| 真库对象总数 | **28 张表 + 1 个视图** |
| C3 §6.1 的自我定位 | 「当前最小核心表集（**建议** 18 张以内）」——**措辞是"建议"** |
| 宪法内部是否一致 | **不一致**：§2.2 用 snake_case 单数（`evidence_fragment`），§2.3 用 CamelCase 概念（Entity / Event） |
| 宪法是否强制过物理名 | **没有** —— §6.1 是"建议"，不是强制 |
| 已有的误判记录 | `SCHEMA-DIFF-20261002` 记录了至少一次"按宪法名查不到表" |
| 甲乙丙三类之外的"结构分裂" | **2 处**（`historical_space_claim` 拆 5 张、`relation_claim` 双存储） |

**最要紧的一条**：宪法与真库之间**至今没有唯一对照** —— 唯一的对照是一份**活在脚本里的数组**（`gen-schema-diff.mjs` 的 `G` / `EXTRA`）。这与今天已修的多处"知识活在脚本里、没有登记"是同一个病。

**不改的代价**：分叉会随新表继续增长，且每次都要靠人去读脚本才知道"这个概念落在哪张表"。

## 影响谁

| 受谁影响 | 会怎样 |
|---|---|
| **选 A** | 新增 `specs/DATA_CONTRACT.md` 的映射段 + C3 §6.1 一句说明 + 一个守卫；**真库不动** |
| **选 B** | 约 20 张表 + 外键 + 视图 + 触发器 + 20 余个脚本 SQL；**有数据迁移风险** |
| 体验层 | **不受影响**（前端不读数据库，读已生成的体验 JSON） |
| 与 ESC-02 的关系 | 丁类里的 `relation_claim` 双存储**属 ESC-02**，本提案**不处理**它 |

## 我已查清（不需要你回答）

1. **分叉有多少种？** 四种（甲/乙/丙/丁）。我已逐个列出，并标出**哪些根本不是命名问题**。
2. **重命名表的代价到底多大？** 真库 28 张表需改约 20 张；连带外键、视图、4 个触发器与脚本内 SQL；**且表里有真实数据**。→ 这是我建议不做 B 的依据，**依据是实测的表数与依赖**。
3. **宪法是否强制过物理名？** **没有**。C3 §6.1 的措辞是"建议"。所以选 B 不是"恢复宪法"，而是**先把建议升格为强制、再执行**。
4. **`claims` / `evidence` / `relations` 为什么不在 C3 §6.1 里？** 它们是 001 迁移建的基础对象；C3 §2.2 只列了 `evidence_fragment` / `claim_evidence_link` 等。它们属上面那"真库有、宪法未列"的 8 张之一，**方案 A 会把它们一并登记**。

## 怎么回滚

- **方案 A**：新增的映射段与守卫**可整段删除**；**不动真库、无迁移、无数据风险**。
- **方案 B**：**不可轻易回滚** —— 表名已改、数据已迁，需靠迁移历史反向重命名，且期间任何外部引用都会断。
- **方案 C**：无需回滚，因为什么都没做。
