五个结构性差异（按严重度）

1. 命名分叉（最该修）：宪法 PART VI 用单数（source_record / event / relation_claim / visual_asset / evidence_fragment / human_review）， 真库是复数 + 前缀（source_records / cultural_events / cultural_relation_claims / visual_assets / evidence_fragments / human_review_decisions）。 后果：任何按宪法名写 SQL 或查 schema 的人都会误判表是否存在 —— 我前面把已存在的 visual_entity_links 误判为缺失，就是活例。
2. 双 relation 存储：relations(001，365 行) 与 cultural_relation_claims(008，8 行) 并存， 宪法假设单一 relation_claim。Agent 会读到两份不一致的关系。
3. epistemic 双轴未建模：verification_status（8 值，管道阶段）与 epistemic_status（6 值，认识档位）两条轴并存，宪法只写了后者，读 status 易混淆。
4. 三个 P1 缺口未建：modern_location（触及「现代坐标≠历史位置」红线）、open_question、external_node。 其中 modern_location 自 09-26 审计识别后一直停在「待你拍板」。
5. raw 不进库（设计选择，非缺陷）：raw_item 无表是有意为之 —— raw 永留文件系统，库只存元数据 + raw_path 指针。 但宪法未写明此决策，应补一句对齐。

结论

概念覆盖率：高。L0–L5 几乎所有宪法对象在真库都有落点，红线由触发器落地（如 vel_confirmed_requires_evidence、review_queue_tier_c_guard、discovery_not_publishable_guard）。
物理/命名一致性：低。单数 vs 复数+前缀的分叉，是造成「以为缺表」的根源。
真空缺仅 3 个 P1：modern_location、open_question、external_node；另有 source_version 为低优先主动取舍。
真实风险不在「表缺」，而在「表建了没填」：如 visual_entity_links 已建但仅 22 行；cultural_conflicts 1 行等。
