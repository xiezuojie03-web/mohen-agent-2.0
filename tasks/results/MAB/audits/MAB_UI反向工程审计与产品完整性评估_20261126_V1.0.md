## 0｜执行摘要

### 0.1 核心裁决

**墨痕当前最大的问题不是单纯的工程施工不到位，而是产品体验设计、已存在的工程能力和跨空间业务关系没有形成一致的用户体验。设计成熟度不足与工程表达/接线不足同时存在；从用户感受看，产品设计与体验整合是更上层的主要缺口。**

当前工程已经拥有相当多真实业务基础：Studio项目、研究任务、Agent研究调用、受控生产请求、导演方案、作品修订、审核发布、知识资产检查、账户角色治理、EXP查询和专题体验引擎。不能把它们说成空壳，也不应推翻D00—D05、G0—G5、Runner/Registry或现有身份/数据底座。

但这些能力没有共同组成一个普通用户可以自然理解的产品：

- HOME仍是功能入口和空态集合，不是知识世界。
- Studio有真实业务链和Agent调用，但用户看见的仍较像生产操作台；研究过程、Agent判断、知识与作品双产出、局部改稿和移动端工作区体验没有充分表达。
- Admin的审核、发布、资产检查和用户管理比CEI旧原型更完整，但缺少上下文式Agent治理辅助，知识资产治理也仍以项目内检查为主。
- EXP的双组件框架和专题体验引擎有可继承基础，但通用探索与专题舞台分离，Agent判断没有稳定驱动通用舞台，探索历史没有形成完整可恢复资产。
- WATCH能消费合法发布修订并呈现章节/媒体依据，但当前是图文与章节阅读，自动翻页不等于视频播放；已有观看进度API没有在WatchGallery中形成可见的保存/恢复调用。
- 用户个人空间没有成为产品工作面；身份菜单、探索会话、作品项目和观看进度分别存在，但没有统一的个人资产与长期关系空间。

### 0.2 五大空间成熟度总表

| 产品空间 | 当前用户体验判断 | 工程基础 | 主要缺口 | 成熟度 |
|---|---|---|---|---|
| HOME | 功能入口，不是知识世界 | 静态首页和模式路由 | CEI知识组织没有进入当前页面；无真实策展内容/对象/关系 | NON_COMPLIANT |
| Studio | 能发起研究和创作，但用户流程不够自然，Agent过程不够可感知 | 项目、研究、受控生产、导演、修订、投稿链 | 交互语言、研究可视化、Agent协作表达、窄屏工作区 | PARTIAL |
| Admin | 治理功能较完整，Agent辅助和整体视觉体验不足 | 审核、发布、知识资产检查、用户/权限API | 跨域治理视图、Agent辅助判断、统一的治理任务上下文 | PARTIAL |
| EXP | 双组件基础成立，但通用探索与专题体验没有合流 | Explore、Agent Research、Experience Engine、专题舞台 | Agent→舞台联动、证据焦点、主题交接、跨会话恢复 | PARTIAL |
| 我的墨痕 | 尚未形成独立个人空间 | 账户、项目、作品、探索会话、部分观看进度底座 | /me工作面、收藏、笔记、贡献台账、个人知识、隐私与Agent上下文管理 | NOT_IMPLEMENTED |

**当前不具备面向外部用户开放并承诺持续使用的完整产品条件。** 这不是说所有工程都不能运行，而是公共知识世界、连续探索、可用创作、个人资产和跨空间Agent关系尚未共同形成可验收闭环。

### 0.3 本轮最重要的决策

1. **M5 Studio仍保持当前最高工程优先级。** 本审计不改变PLAN V1.7的施工顺序，不插入EXP或个人空间施工，不要求重做已完成的D/L/G与生产主线。
2. **HOME可以进入正式工程衔接，但不应直接按当前GitHub首页改造。** 以CEI UI工程迭代交付包选定的HOME V1.8.3为结构/交互基线，吸收CEI C步“多尺度策展知识世界”的有界内容组织深化，并使用公众体验视觉规范V1.0；先补齐可回读的原型源文件、模块/数据/动作映射和真实内容资格，不要求重新开展大规模视觉研究。R5概念图制作仍是独立授权事项，不作为当前工程衔接的默认前置。
3. **Studio不推翻底层架构，必须定向深化用户工作流程和可视化。** 内部D/L/G阶段应由系统承担，用户处理的是目标、关键判断、授权、编辑与确认。
4. **EXP停止大规模理论研究，推荐采用一项真实主题的小范围可运行体验验证。** 以一个合法、有真实材料和可核验依据的主题，验证双组件、Agent、舞台、证据、回退和当下生活联系。
5. **个人空间纳入整体产品架构和后续计划，但不挤占M5。** 以正式一级/me工作面建设，不做第四种历史内容模式，也不另建用户身份、项目或作品事实源。

## 1｜审计目标、基准与证据边界

### 1.1 审计目标

本轮从用户目标和实际UI开始，沿以下路径反向追溯：

用户目标 → 操作流程 → 页面信息与视觉表达 → 组件/状态/交互 → API与业务逻辑 → Agent调用 → 数据模型与持久化 → 身份/权限/治理 → 工程验收。

本轮审计范围是HOME、Studio、Admin、EXP、WATCH及用户个人空间之间的完整产品关系。WATCH作为五大空间之间的必要消费节点纳入整体旅程检查。

### 1.2 正式设计依据

- MHKA-00《治理与权威生效章程》：产品/知识/Agent/工程的语义责任分离，设计批准、工程应用、运行验证和生产授权不得混同。
- MHKA-01《价值战略与演化方向》：在广阔历史文化知识中发现当下生活的乐趣与意义；EXP为长期核心用户价值，Studio承担自主研究创作和知识资产积累。
- MHKA-02《人文产品与体验》：HOME、Studio、WATCH、EXP、Admin的职责；Studio自然语言研究创作、三工作面协同、窄屏工作区切换、研究与作品双产出；EXP双组件及证据联动；Admin治理职责；人文体验验收。
- MHKA-03《知识世界与数据架构》：知识对象、证据、关系、版本、资格、用途和撤权语义；正式知识资产与作品、研究候选、个人笔记分账。
- MHKA-04《Agent与专业能力》：Agent意图理解、检索、受托研究、导演与工具调度；Agent不自签Gate，不将候选冒充事实。
- MHKA-05《工程实现与运行架构》：API、身份、权限、数据持久化、测试、部署、运行和安全的唯一工程责任。
- CEI-01任务书V4.1及C/D/E/F现行报告。
- CEI HOME R1—R5报告、R1—R4综合修订、CEI UI工程迭代交付包、公众体验与个人空间视觉设计规范V1.0。
- MAB上一轮工程全面审计报告V1.0、当前CURRENT.md和PLAN V1.7。

### 1.3 工程基线核验

当前main为 b9de0d29fed4ef6fa0f29ce2441b97ce814b83c7。对照e5c36922，之后五个提交只修改CURRENT.md、PLAN.md、progress.md和上一轮审计报告，没有业务代码变更。因此本轮对页面、组件、API和数据调用的静态代码判断适用于当前main。

上一轮MAB审计报告的基准为e89e33101ba5351b12a71f1f1e0805b51f1e5f83。本轮不覆盖其历史结论，而是在当前main上从UI和用户流程补充反向审计。

### 1.4 证据等级与限制

本轮实际读取了GitHub main中的页面路由、主组件、部分CSS、关键API、Agent服务、数据库迁移文件及CEI/MHKA报告。**本轮没有启动本地或云端浏览器，没有使用真实用户账号进行交互，没有执行Supabase实时SQL，也没有重跑端到端测试。**

因此：
- 本报告可以确认源码中存在的路由、组件、调用、字段、状态和明确缺失的接线。
- 不把静态代码存在等同于运行成功、数据库迁移已应用、真实用户权限通过或视觉效果已验收。
- CEI报告中记载的历史Chromium测试及SHA仅按历史证据引用，不升级为本轮实测。
- 当前仓库没有找到CEI报告所引用的完整统一HTML原型文件，也没有找到可直接回读的HOME V1.8.3完整源文件。本轮依据其现行研究报告和交付包判断设计方向，但不声称重新检查了这些HTML的全部细节。
- 沪上经纬旧项目和早期双组件/五图设计仅作为历史设计来源比较；不把旧页面骨架或旧项目作为当前工程依赖。

### 1.5 历史设计继承判断

历史设计中值得保留的是持续视觉舞台、Patch-not-Replace、ExperienceState continuity、Evidence-aware Replan、Agent与视觉表达之间的权威转移，以及墨痕在场意识。旧版timebar、固定舞台、叙事区、action dock、Prev/Next和固定证据抽屉等物理页面骨架不应整体照搬。

五图UI提供了区域和功能职责参考；双组件定义EXP的体验身份与主次，三区域定义可变化的布局空间，两者并不冲突。当前应继承体验原则和可验证的交互能力，而不是按历史页面数量或布局形式决定新工程。

## 2｜五大空间专项审计

### 2.1 HOME｜从功能入口转向知识世界

**实际页面：** apps/web/app/page.tsx；全局导航：apps/web/app/components/GlobalNav.tsx。

当前首页实际包含品牌主张、创作入口、了解墨痕按钮、Studio/WATCH/EXP三个模式卡片，以及“最近发布作品”“我的创作任务”“知识资产概览”三个空态面板。页面没有从知识读模型加载真实策展主题、对象、原件、关系或知识变化；也没有从首页把具体主题场景传递给EXP的实现。

这与MHKA-02和CEI HOME目标不符。首页的主要内容单位不应是模式入口卡片，而应是用户能进入的历史文化发现情境。

CEI C步建议的“多尺度策展知识世界”方向是有价值的：世界视野、主题场景、具体对象、有关联理由的发现；时间、地域、人物、器物、思想和日常生活是可组合观察视角，不应变成互斥分类树。

**继承和边界：**
- 继承HOME V1.8.3已认可的策展入口、连续漫游、对象进入统一EXP、墨痕低干扰在场和返回锚点。
- 不继承当前GitHub首页的入口卡片墙作为主页主体。
- 不把Figma长页面的纵向模块清单直接当作新首页结构。
- 将CEI C步的多尺度组织作为V1.8.3内容组织的定向深化，不推翻V1.8.3交互基线。
- 只呈现真实、合法、当前可公开消费的材料；研究候选、外部线索、设计夹具和正式合格资产必须有不同身份表达。

**裁决：** HOME设计方向已经足以进入工程衔接；当前GitHub首页不符合目标。工程衔接的前置材料是可回读的V1.8.3交互源、模块/数据/动作映射、真实内容资格与权利说明、HOME→EXP上下文合同。R5概念图制作尚未授权，不应擅自把概念图制作变成新的工程阻断。

### 2.2 Studio｜真实生产能力没有转化成自然的智能创作体验

**实际页面和调用：**
- apps/web/app/studio/page.tsx
- apps/web/app/studio/StudioWorkbench.tsx
- apps/web/app/studio/desk/ImportForm.tsx、ProjectNotebook.tsx、ResearchPlan.tsx
- apps/web/lib/mohen-agent/research.ts
- apps/web/app/api/studio/research-tasks/route.ts
- apps/web/app/api/studio/research-tasks/[id]/production/route.ts
- apps/web/app/api/studio/director-plans/route.ts
- apps/web/app/api/studio/works/route.ts
- apps/web/app/api/studio/works/[id]/submissions/route.ts

**已存在的真实业务能力：**
- Studio服务端要求登录后进入工作台。
- 工作台具有自然语言委托、项目/研究底稿、研究任务恢复、资料读取、来源与权利提示、受控正式生产、生产状态轮询、A/B导演方案、分镜和作品修订、提交审核等调用。
- research.ts真实调用Agent Runtime的understand、检索、裁决、风险守卫和外部来源发现；研究结果不是任意生成的事实，材料有认识状态和来源。
- 正式生产由Creator显式发起，受项目、原件、来源登记、权利、Registry、预算、授权和回执约束。
- 作品提交和Admin审核发布已有独立接口。不能把现有生产链说成完全没有实现。

**主要用户体验问题：**

1. 项目身份被设计为“对用户隐形”，以自动建立底稿和抽屉恢复为主。降低了项目操作负担，但用户仍需要知道当前研究归属于哪一个持续项目、有哪些未完成事项和产出。
2. 页面把创作划分为对话与构思、受托研究与编导、预览与修改、审核与发布；研究区又显示资料检索、筛选、核验、编导、分镜等节点。局部说明中仍出现D00—D05、G0—G5、L0—L5和独立门等内部工程语言，违反“由Agent承担专业流程、用户只处理本人决策”的体验目标。
3. 研究进展虽然由真实材料数量和生产状态派生，但“有材料”“候选”“独立资格通过”不是同一件事。现有界面容易把用户带进生产阶段管理，而不是帮助用户理解墨痕发现了什么、为什么这样判断、还有什么不知道。
4. Agent确实参与意图理解和研究，但页面呈现主要是mohenLine、材料列表、缺口、A/B方案和“墨痕在构思/写分镜”的状态。任务拆解、研究策略、来源比较、证据冲突、研究发现、方案取舍和认识增量没有形成连续可审阅的Agent工作过程。
5. 右侧作品区有分镜/脚本、故事结构、画面风格、配音旁白、背景音乐等编辑入口，但目前不能据此认定已经形成随研究逐步成形、可局部改稿、可视化预览和可比较的完整作品舞台。
6. studio.css在宽屏采用三工作面；1100px以下收敛为单列，不能替代MHKA-02要求的窄屏三个工作区切换。当前代码未显示完整的移动端工作区切换机制。
7. 外部模型授权提示和正式生产授权是必要的真实用户决定，不应为了“智能化”而取消；但日常研究流程不应让用户逐项处理内部工具选路或生产阶段。

**建议的Studio用户主线：**

表达创作目标 → 墨痕理解并必要澄清 → 给出研究方向与理由 → 组织材料、证据、来源和缺口 → 展示研究发现及可复用知识工作成果 → 提出有真实差异的导演方案 → 用户选择并对局部内容修改 → 作品逐步形成 → 保存版本/继续项目 → 提交审核。

其中知识资产和作品修订双产出继续分账；D/L/G留在后台专业生产与资格链，不作为创作者必须理解的导航语言。

**裁决：** Studio需要定向重构用户工作流程和交互表达，但不需要推翻底层生产架构。当前最重要的是把已存在的Agent/生产能力转成用户可理解、可检查、可继续的协作过程，并完成真实浏览器端到端验收。

### 2.3 Admin｜治理能力存在，Agent辅助治理缺位

**实际页面和调用：**
- apps/web/app/admin/page.tsx
- apps/web/app/admin/AdminWorkbench.tsx
- apps/web/app/admin/KnowledgeAssetInspector.tsx
- apps/web/app/admin/knowledge-asset-view.ts
- apps/web/app/api/admin/users/route.ts
- apps/web/app/api/admin/users/[id]/status/route.ts
- apps/web/app/api/admin/acl/route.ts
- apps/web/app/api/admin/rights/invalidate/route.ts
- apps/web/app/api/admin/publications/route.ts

当前Admin代码有九个工作区：运行概览、资格审核、作品审核、发布管理、知识资产、权限与撤权、用户管理、数据统计、系统设置。它已经接入作品审核/发布、用户列表、账户状态、角色管理、知识资产检查和撤权接口。

因此，CEI-E早期原型中“缺少知识资产治理和用户管理入口”的判断，不能直接照搬成当前GitHub工程结论。现有Admin已经比该原型覆盖更多真实业务。

**仍然存在的缺口：**
- KnowledgeAssetInspector以项目为入口检查资产、来源、修订、权利、使用记录和撤回；尚不能据此认定已经具备面向全平台全部知识资产的统一目录、跨资产关系和完整运营治理。
- Admin没有发现与Agent Runtime或MohenPresence连接的上下文式治理辅助。界面能显示状态和按钮，但没有在具体资产/作品/权限任务中解释风险、发现缺口、比较修订、推荐合法下一步。
- 用户治理接口主要覆盖账户列表、角色与状态操作；真实数据库授权、敏感信息查看审计、隐私请求、贡献处理等是否完整，需要进一步运行核验。
- 当前视觉设计规范V1.0明确不覆盖Admin内部布局和视觉改版。Admin视觉质量不能由公共页面的统一令牌自动保证；本轮没有真实浏览器截图，故不把主观观感写成视觉实测结论。

**Agent治理辅助建议：**
- 作品审核：摘要事实/权利风险、指出引用和修订差异、列出缺少的人工确认项。
- 知识资产：解释来源链、认识状态、资格和权利缺口，提出补证或撤权建议。
- 用户与权限：解释角色变更影响、异常访问和最小权限风险，生成可审阅的操作摘要。
- 运行概览：把失败任务、预算异常、失效依赖和待人工决定事项组织为有依据的行动清单。

Agent只能提出建议、解释依据和准备操作；专业Gate仍由独立Reviewer签发，Operator仍对运营发布/撤回负责。不能以Agent聊天代替治理流程，也不能让Agent代签。

**裁决：** Admin功能结构基本可继承，不需重做九个工作区。应深化治理信息组织、上下文辅助和视觉层次；Agent采用嵌入式治理建议，不新增无意义聊天功能。

### 2.4 EXP｜双组件成立，通用探索与专题舞台尚未合流

**实际代码分为两条体验路径：**

A. 通用Explore：
- apps/web/app/explore/page.tsx
- apps/web/app/explore/ExploreWorkbench.tsx
- apps/web/app/explore/ExplorePresentation.tsx
- apps/web/app/api/explore/sessions/route.ts
- apps/web/app/api/explore/sessions/[id]/query/route.ts
- apps/web/app/api/explore/sessions/[id]/insight-views/route.ts
- apps/web/lib/mohen-agent/research.ts

B. 专题Experience：
- apps/web/app/experience/jinze-water-net/ExperienceShell.tsx
- apps/web/app/experience/jinze-water-net/MohenPresence.tsx
- apps/web/app/experience/jinze-water-net/AskBar.tsx
- apps/web/app/experience/jinze-water-net/surfaceRegistry.tsx及相关surfaces
- apps/web/app/experience/lvzhiqiu/A001Experience.tsx及相关组件
- packages/experience-engine

**双组件结论：**

视觉舞台与墨痕叙事的职责边界成立。证据应是按需展开、随当前判断联动的辅助信任面板，不应与双组件并列争夺舞台主位。三区域是布局可能性，不是永久三栏法令。历史EXP-0002和V0.9.1最值得继承的是Persistent Canvas、Patch-not-Replace、状态连续性、Evidence-aware Replan和权限/权威转移，而不是旧页面的固定布局。

**当前代码已经实现的部分：**
- ExplorePresentation有叙事隐藏/提示/展开、证据关闭/概览/展开/细读等独立状态，并支持停靠/悬浮和尺寸调整。
- ExploreWorkbench可以建立探索会话、调用Agent研究、显示材料/缺口，并生成带来源的关系图候选。
- ExperienceShell使用Experience Engine、Surface Registry、Evidence-aware选择、MohenPresence和AskBar；AgentDecision可以进入导演层并推动场景/视觉表达变化。
- 金泽和绿之丘专题体验分别使用冻结样例/真实生产读模型等不同来源，不能把两者证据身份混为一谈。

**主要缺口：**
1. 通用Explore的Agent查询调用runResearch(question)，默认generic；返回回答、材料和缺口，但当前通用页面没有把AgentDecision的主视觉判断稳定接入中心舞台状态。
2. 通用页面仍以关系/时间/空间/故事视角切换为主要舞台入口，用户更多是在切换视图，而不是由问题、观察和Agent判断推动连续的场景变化。
3. 专题Experience的舞台与Agent联动较强，但没有在首页和通用Explore主组件中形成清晰的主题进入、继续探索和返回路径。
4. Explore会话表保存intent、origin_snapshot、owner、title和archived等信息，但当前查询路由返回Agent结果，没有把每轮问答、材料焦点、舞台变化、证据选择和下一步写成完整探索记录。
5. 已有会话重命名/归档/分享接口没有在当前Explore主界面形成完整的历史列表与恢复操作；分享接口返回链接不等于已完成可访问的分享体验。
6. insight-views路由调用generateInsightView时没有显式传入授权grant；当前调用点不足以证明该LLM图见能力在所有环境均具备合法外发授权和可用运行条件。
7. CEI-D已指出原件首屏主视觉延迟、证据焦点错配、主题场景上下文交接、关键词/正则路由、窄屏控件重叠等问题。当前GitHub通用Explore并不能证明这些设计问题已被解决。
8. 没有本轮真实浏览器和真实用户证据，不能认定专题体验具有持续探索吸引力或跨题材通用性。

**三条路径比较：**

| 路径 | 体验提升 | 设计成熟度 | 不确定性 | 改造量/成本 | 可逆性 | 用户证据 |
|---|---|---|---|---|---|---|
| 继续大规模设计研究 | 中，可能继续澄清细节 | 双组件和主次关系已明确，剩余多为局部问题 | 研究边界和准出时间不确定 | 高，且容易重复 | 高 | 仍主要是设计证据 |
| 直接全量工程衔接 | 高潜力 | 仍有证据焦点、主题交接和通用Agent舞台联动未验证 | 高 | 高 | 中低，易固化错误结构 | 可获得工程证据，但返工成本大 |
| 单一真实主题小范围可运行体验 | 高，直接验证关键链路 | 双组件框架、Agent、舞台、证据已有可继承基础 | 可限定在一个主题和一条主线 | 中低 | 高，可隔离试验 | 能获得真实操作、运行与用户判断证据 |

**唯一推荐：路径3——选择一个真实历史主题，完成双组件的局部可运行体验验证，再决定是否深化设计。**

建议以当前已有专题能力和真实材料条件可支持的金泽主题作为试验候选；试验前必须核实当下可用的来源、资格、权利和舞台数据，不把冻结JSON或设计夹具当正式知识。试验只验证对象进入、Agent理解、用户转向、舞台变化、证据同步、未知边界、回退/恢复及与当下生活的具体联系，不把专题试验直接固化为全平台模板。

**裁决：** 停止新增大规模EXP理论研究；不推翻双组件；不直接全量工程化。先做单主题可运行体验验证。

### 2.5 用户个人空间｜正式一级个人空间，不是账户菜单

**当前工程实际表现：**
- GlobalNav有用户头像、登录/注册、角色显示和退出登录。
- API有当前会话身份读取。
- Explore有探索会话创建、读取、重命名、归档和分享接口。
- Studio有项目、研究任务、作品和修订。
- WATCH有观看进度API和按用户/作品修订保存的设计。
- 但没有独立/me页面路由，没有个人首页，没有统一个人资产列表，没有收藏/笔记/个人知识空间/贡献处理记录的完整用户端工作面。

**个人空间定位：**

“我的墨痕”应成为围绕用户身份、项目、探索记录、作品、收藏、贡献和个人知识形成的长期连续性空间。它不是第四种历史内容模式，也不是社交信息流。桌面快速抽屉可以保留，但不能承担全部个人空间职责。

**建议一级信息架构：**
1. 我的首页：继续探索、继续创作、最近保存、待处理事项。
2. 探索与收藏：探索时间线、收藏对象/主题/作品/来源、精确恢复。
3. 创作项目：Studio项目、研究任务、知识工作资产状态、草稿、作品修订、审核反馈、发布状态。
4. 我的贡献：提交记录、授权、候选身份、待审/补充/接受/拒绝、撤回和处理反馈。
5. 个人知识空间：私有专题集、笔记、材料链接和对象关联；默认私有。
6. 账户与隐私：身份、偏好、通知、数据导出/删除、授权管理和安全控制。

**数据和权限边界：**
- 复用现有用户、Studio项目、研究任务、作品/修订、Explore会话和Watch进度，不建立第二套项目/作品真值。
- 收藏、私人笔记、个人专题集和贡献台账属于需要新增或补齐的用户资产能力。
- 每项个人资产明确owner_user_id、项目/对象/修订引用、可见范围、分享状态、Agent可读范围、授权时间和撤回/删除语义。
- 私人笔记和探索联想默认不进入Agent上下文；用户可按项目或单次任务明确授权。
- 用户个人资产不能自动升级为正式知识资产；候选贡献仍须通过原有证据、权利和独立Gate。
- Admin平台治理与个人空间本人控制分开；管理员不得默认读取用户私人笔记和探索记录。
- Agent长期上下文必须有用户可见、可授权、可撤回、可清除的范围，不得把跨空间行为记录默认拼成隐形用户画像。

**分阶段建设：**
- 先完成产品架构、数据边界和权限合同；
- M5完成后先做个人首页、继续探索/创作、项目/作品和收藏的基础工作面；
- 再补贡献台账、个人知识集和笔记；
- 最后建设用户授权的Agent长期上下文和基于个人兴趣的发现。
  
**裁决：** 个人空间是平台长期留存能力的必要组成，但属于未来产品能力和架构准备事项，不进入当前M5施工主线。

## 3｜五大空间之间的整体体验关系

### 3.1 目标产品关系图

HOME（公共历史文化知识世界）
  ├─ 主题/对象/发现情境 → WATCH（合法作品消费）
  ├─ 主题/对象/问题 → EXP（自主探索）
  └─ 用户产生创作意图 → Studio（研究与创作）

WATCH ↔ EXP：从作品版本/章节/时码进入探索，带锚点返回原观看位置。

EXP → Studio：用户主动选择将探索问题、对象、来源和证据带入研究创作；不是自动把所有探索转成项目。

Studio → Admin：提交精确作品修订，进入独立审核、权利核验、运营发布。

Admin → WATCH：合法发布或撤回，WATCH只消费当前有效公开修订。

/me个人空间横跨HOME、EXP、WATCH、Studio：保存探索、收藏、项目、作品、贡献和个人知识；在用户明确授权下向Agent提供持续上下文。

上图是目标产品关系，不代表当前所有路径已实现。Admin负责审核、发布、权限和平台治理，不是公众内容入口；个人空间横跨各产品空间，保存用户自己的资产和连续性。

### 3.2 六条关键用户旅程的现状

| 用户旅程 | 当前实现 | 状态 | 关键断点 |
|---|---|---|---|
| HOME发现主题→WATCH | HOME有WATCH入口，WATCH有合法发布作品目录 | PARTIAL | HOME当前没有真实主题/对象策展内容，无法形成主题驱动的观看 |
| WATCH→EXP→返回WATCH | 有Watch作品、Explore会话和返回接口 | NOT_IMPLEMENTED/PARTIAL | WatchGallery未见EXP入口和会话锚点交接；Watch进度API未接入页面保存/恢复 |
| EXP发现→Studio创作 | EXP和Studio分别存在 | NOT_IMPLEMENTED | 未见将当前探索对象、问题、证据和焦点直接带入Studio的用户操作闭环 |
| Studio→Admin审核→WATCH | Studio提交接口、Admin审核/发布、WATCH读取发布目录 | PARTIAL | 代码链存在，但本轮未进行真实Creator/Reviewer/Operator浏览器端到端验收 |
| 用户资产沉淀到个人空间 | 底层项目/作品/探索会话/部分观看进度存在 | NOT_IMPLEMENTED | 没有统一/me工作面、收藏、个人笔记和贡献记录 |
| 再次进入HOME/EXP个性化发现 | Agent分散存在于Studio和EXP | NOT_IMPLEMENTED | 没有用户授权的跨会话兴趣上下文与个人资产回流 |

### 3.3 Agent在五个空间的连续角色

| 空间 | Agent应承担的角色 | 当前情况 |
|---|---|---|
| HOME | 低干扰策展伙伴，解释主题组合理由、提出发现方向 | 当前首页没有接入Agent |
| EXP | 观察引导者、关系发现者、解释者和视觉舞台调度者 | 通用Explore部分实现；专题Experience能力较强但未统一 |
| Studio | 研究伙伴、资料组织者、证据判断辅助者、导演和创作协作者 | 有真实Agent调用，但过程表达不足 |
| Admin | 治理分析助手、异常解释者、补证/处理建议者 | 未发现实际Agent接入 |
| WATCH | 轻量解说和依据辅助，不打断作品观看 | 当前以作品内容和来源面板为主，未见Agent接入 |
| 我的墨痕 | 在明确授权范围内记住研究方向、帮助继续未完成工作 | 尚无个人空间及授权上下文管理 |

统一的是Agent身份、权限与用户连续关系；不同空间的Agent介入强度和任务职责应不同。不能把一个全局聊天框当成跨空间智能体能力。

## 5｜设计问题与施工问题责任划分

## 6｜设计补强清单

### 6.1 必须重新设计或重组

1. HOME从入口集合转为策展知识世界；不能只增加几个卡片或换背景图。
2. Studio创作者工作流程：将后台生产阶段翻译为用户任务语言，重组Agent理解、研究进展、证据、知识产物、作品舞台和用户确认点。
3. EXP通用体验中Agent决策、舞台变化和证据焦点的协同机制。
4. 个人空间从用户菜单升级为正式一级工作面。
5. 五空间之间的上下文交接：主题/对象、来源、证据焦点、作品修订、探索位置、用户授权和返回锚点。

### 6.2 必须深化，但不推翻现有结构

1. Admin的九个治理工作区和现有API；重点补充Agent上下文式风险说明与行动建议。
2. Studio桌面三工作面；保留委托/研究/作品职责，改进过程表达、编辑预览和移动端切换。
3. EXP双组件和三区域状态规则；深化二级视觉组件、舞台动作和证据同步。
4. WATCH图文/章节体验；补齐进度恢复、EXP往返和真实媒体能力边界。
5. 全局Agent身份与介入原则；不同空间按任务改变介入强度，不重复建设Agent Runtime。

### 6.3 可以直接继承

- D00—D05、L0—L8、G0—G5和既有Runner/Registry生产主线。
- Studio项目、研究任务、受控原件、来源登记、研究读取、导演方案、作品修订和投稿/发布服务。
- Admin现有Reviewer/Operator职责、作品审核、发布/撤回、用户角色管理、知识资产检查器。
- EXP的Experience Engine、Surface Registry、MohenPresence、AskBar、专题舞台和Evidence-aware选择机制。
- WATCH合法作品目录、不可变修订、媒体权利复核和章节结构。
- 现有用户身份和业务数据；个人空间只做聚合、索引和新增个人资产，不建第二套事实源。
- CEI公众体验视觉规范V1.0的暖纸、温润白、青瓷绿、松柏绿和明亮清润原则；不将该规范误用为Studio/Admin内部布局的既定授权。

### 6.4 需要通过工程试验验证

- HOME主题场景进入EXP、返回后恢复策展位置。
- Studio真实Agent研究过程、研究/知识双产出、作品逐步形成和定向修改。
- EXP单主题中Agent决策是否实际改变视觉舞台、证据是否跟随焦点、用户能否自由转向并返回。
- WATCH真实保存/恢复观看位置，以及WATCH↔EXP的修订和时码锚点。
- AdminAgent对真实治理对象的辅助建议是否有依据且不越权。
- 个人空间跨模块恢复、权限隔离和Agent上下文授权。

### 6.5 应放弃的历史做法

- 以模式入口卡片墙作为HOME主体。
- 把五图的物理三区域直接固化成EXP所有状态下永久三栏。
- 把Studio内部D/L/G生产流程当成创作者的操作菜单。
- 把通用聊天窗口当作Admin或跨空间Agent能力。
- 把EXP设计成固定剧情章节或预制热点路线。
- 把关系/时间/空间/故事四个技术视图当成用户必须掌握的探索导航。
- 把WATCH自动翻页称为视频播放。
- 把个人空间做成社交信息流、签到积分、公开用户画像或自动向Agent开放的私人资料库。
- 直接照搬沪上经纬旧页面或旧EXP固定页面骨架。

## 9｜与PLAN V1.7的关系及唯一推荐顺序

### 9.1 对现有施工计划的判断

PLAN V1.7已充分覆盖M5的Studio、Admin、作品修订、审核发布、WATCH和知识资产交接，并要求同一真实作品完成完整垂直切片。当前计划并没有充分覆盖HOME工程衔接、EXP用户体验试验和正式个人空间，但这不构成现在修改M5施工顺序的理由。

- **Studio：** 当前M5优先级不变。Studio体验补强必须服务于真实M5流程，不另起一套项目/Agent/作品正文。
- **HOME：** 可以在M5期间并行完成非代码的工程交接准备、原型源归档、组件/数据/动作映射和内容资格盘点；实际代码实施须服从Owner当前施工授权和M5节奏。
- **EXP：** 不进入当前M5主施工；在M5关键体验完成后，用一个真实主题开展局部工程试验。
- **个人空间：** 当前只形成产品架构、数据/权限边界和未来节点建议；不得新建/me代码、收藏/笔记数据库或Agent长期记忆功能来抢占M5。
- **Admin：** 现有审核/发布/权限能力继续随M5验收；Agent治理辅助作为后续局部设计深化，不改变专业Gate与Operator责任。
- **WATCH：** 继续按M5轻量消费边界验收；不能把当前图文章节阅读描述为完整视频能力。

### 9.2 唯一推荐的后续工作顺序

1. **完成当前M5 Studio真实用户式端到端验收。** 继续按CURRENT和PLAN既定的Owner体验入口执行，先确定真实Creator→研究/生产→作品修订→Admin审核/发布→WATCH消费的体验断点。审计不要求重做已经验收的D/L/G或CI。
2. **并行完成HOME工程交接准备，不先动业务代码。** 将V1.8.3原型源、CEI C步多尺度内容组织、视觉规范V1.0、真实内容/资格/权利和EXP上下文映射整合为一份可施工交付；确认工程交付包与CEI任务书的授权状态后，再按Owner批准的窗口实施。
3. **M5 Owner验收后，实施HOME。** 先建立真实主题/对象内容入口和HOME→EXP→返回闭环，再扩展内容广度；不制作大量新概念图，不把演示内容冒充正式知识资产。
4. **选择一个真实主题完成EXP局部可运行体验试验。** 重点检验Agent→舞台→证据的联动和真实用户自由探索，不先做全量页面翻新。
5. **对Admin做局部治理辅助和视觉深化。** 以真实资产、审核和权限任务为入口，逐步接入Agent建议和治理上下文。
6. **建立个人空间正式产品与数据权限设计，再分阶段施工。** 先项目/作品/探索恢复，再收藏/贡献/个人知识，最后才是用户授权的长期Agent上下文。

### 9.3 PLAN变更建议

本轮不修改PLAN V1.7的施工节点、授权状态和优先顺序。建议未来在M5 Owner验收后，另行提出以下计划变更：
- 新增HOME UI工程衔接/实施节点；
- 新增EXP单主题体验试验节点；
- 新增个人空间架构与分阶段施工节点；
- 将Admin Agent治理辅助列为后续局部体验深化项。

这些均是变更建议，不是本轮已批准的施工授权。

## 10｜最终必须回答的八个问题

### 1. 墨痕当前最大问题是工程施工不到位，还是产品设计不成熟？

两者都有，但更上层的主要问题是产品体验设计与工程能力之间没有完成统一。底层生产、Agent研究、作品、审核和数据能力已有真实基础；但HOME、Studio、EXP、Admin和个人空间没有共同形成自然的用户旅程。继续只修工程接口，不能自动解决产品体验；继续无限研究设计，也不能代替真实工程验证。

### 2. HOME是否可以依据CEI成果进入工程衔接？

**可以进入正式工程衔接准备。** 当前UI迭代交付包已选择V1.8.3作为唯一结构/交互基线，公众体验视觉规范V1.0已形成工程输入。CEI C步的多尺度知识世界应作为V1.8.3的内容组织深化，而不是推翻它。必须先补齐可回读原型源、真实内容/权利/资格和模块动作映射。R5视觉概念图仍为条件通过且未授权制作，不能把它当成已经完成的交付物。

### 3. Studio是否需要重新设计？

**需要重新组织用户工作流程和交互可视化，不需要推翻底层生产架构。** 现有Agent和生产能力应继续复用；把内部D/L/G阶段翻译成用户语言，让用户看见目标理解、研究发现、证据、待确认事项、作品形成和修改结果。

### 4. Admin如何体现Agent治理辅助？

不增加通用聊天窗口。将Agent嵌入作品审核、知识资产、权利和用户权限等具体治理任务，提供有依据的风险解释、修订比较、补证建议和下一步行动；所有专业Gate、账户权限和发布决定仍由有权角色执行。

### 5. EXP是否停止大规模研究，转向小范围工程试验？

**是。** 双组件总体框架成立，当前缺口可以通过一个真实主题的可运行试验检验。先验证Agent理解、视觉舞台变化、证据同步、自由转向、未知边界、回退恢复和当下生活联系，再决定是否扩大工程范围。

### 6. 个人空间如何进入整体产品架构和未来施工计划？

将“我的墨痕”设为正式一级 /me个人空间，连接探索记录、收藏、Studio项目/作品、贡献和个人知识。复用现有身份、项目、作品、探索和观看数据，不建第二套事实源。先明确用户资产、平台资产和授权Agent上下文的边界；M5完成后分阶段施工。

### 7. 五大空间应该形成怎样的完整体验？

HOME发现主题与对象 → WATCH消费合法作品或EXP继续探索 → EXP围绕用户问题形成新的认识 → 用户选择进入Studio开展研究创作 → Admin独立治理审核和发布 → WATCH消费新作品；整个过程中用户在“我的墨痕”保存、恢复、组织和管理个人资产，并在明确授权下让Agent继续此前的研究。

### 8. 如果现在只能优先做三件事，最值得做什么？

1. **M5 Studio真实完整闭环验收**：它决定墨痕能否自主研究、创作和积累知识资产，是当前施工主线。
2. **HOME按CEI成果进入工程衔接**：它决定用户能否进入一个真正有内容、有发现兴趣的历史文化世界，而不是门户。
3. **EXP单主题真实体验试验**：它决定双组件是否能真正形成Agent引导、舞台变化和认识增量，是墨痕长期差异化价值的验证入口。

个人空间和Admin Agent辅助必须进入产品架构与后续计划，但不应挤占上述三项当前优先工作。
