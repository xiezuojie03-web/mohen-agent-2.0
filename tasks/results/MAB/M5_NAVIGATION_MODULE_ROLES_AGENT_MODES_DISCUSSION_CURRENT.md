### 1.1 产品价值与讨论层次

- **[现行上位合同｜MHKA-01 §1；Owner认可]** 墨痕帮助人在广阔的历史文化知识中发现当下生活的**乐趣与意义**。时间、空间、关系、比较和叙事是理解与发现的方法，不是产品的最终目的。

## 2. Agent最高定位与全程在场（工作性方案，尚待最终审定）

**[Owner基本认可的定位方向＋对智能创作的命名建议]**

> **墨痕Agent是贯穿历史文化研究、创作、观看、探索与治理的「情境感知、人文发现和智能创作伙伴」。** 它理解用户与当前历史文化情境，主动发现有依据、有趣味、与当下生活相连的问题和关系，充分利用研究、分析、构思、编导和多模态表达能力，帮助人把想法转为能核验、能保存、能继续完善的成果。

这里的**智能创作**指Agent的重要能力特色和Studio的主要用法，不表示WATCH、EXP、Admin都必须产出公开作品；Agent的智能协作、工具调度与恢复是支撑能力，而非最高价值定义。

**[待审的全程在场四种机制]** 四者不可混写成「全程高频调用模型」：

1. **可达**：墨痕始终可以被唤起，通常低打扰；在历史视觉舞台中不抢画面，不把所有操作转成聊天窗口。
2. **连续**：在当前权限下知道用户问题、工作对象、历史时空焦点、作品/研究修订、证据与可恢复轨迹；语义状态与界面偏好分开，跨工作面不自动复制越权数据。
3. **判断**：理解当前行动，必要时提出可关闭、可忽略的轻提示；不能以单次停留自动推断永久兴趣或形成未经同意的画像。
4. **行动**：在任务、权限、预算与止损条件满足时才调用工具、模型或正式生产请求；关键副作用必须有具体授权及真实回执。

**[待审的主动性分级]** 静默/随时可问 → 条件化轻提示 → 获明确授权的任务执行。此为产品策略提案，不是新状态机合同；高风险、跨项目、公开发布、外发敏感资料和撤权操作不能靠一条轻提示自动提权。

**[待审的Agent组织逻辑]** 优先分析「可复用Agent能力底座＋角色/工作面策略」，按active_role、consumer、purpose、object、side_effect、预算与主动性限制能力；是否拆为多个专业子Agent，须由真实任务和工程必要性决定，而非预设四套Agent或建立第二条Truth链。

## 4. 模型、工具、知识库与开发平台的分工

**[现行MHKA-04和Agent专业合同]** 产品内Agent负责理解、计划、候选判断、调度、回执与恢复；Skill是可复用方法；Tool/Service/Adapter提供实际检索、GIS、OCR/VLM、计算或Provider连接；Registry描述发现与绑定，不能将声明或激活当作已授权执行。**知识库**是来源、事实、解释、工作资产和作品修订的持久对象及其查询/授权服务，不是另一个主动Agent。

**[现行受托路线，具体主动性待审]**

1. 按用户任务、当前对象和权限确定是否真的需要行动；一般画面切换、合法直接读取、状态恢复不必调用模型。
2. 先复用有权且当前有效的资产、确定性查询和专业工具；对跨证据理解、创意构思、导演生成或自然语言解释，**充分采用有界模型能力**，不能以省Token为由把智能创作退化为固定模板。
3. 对外发资料、Provider与专业Tool核对来源/第三方处理权、最小输入、角色/项目、成本上限、止损和用户授权；费用未知或许可不成立时HOLD或降级，不伪造调用。
4. 形成实际模型/Tool版本、时间、输入输出摘要、成本与ExecutionReceipt；不把单纯模型回答冒充已执行的研究、取得的原件或成功保存。
5. 未验证输出保留候选身份与原文/推断分声部，按T1—T7核验；升为正式历史知识仍由唯一D/L/G与独立Reviewer处理，变为公开作品需Creator/Operator及版权资格处理。

**[现行MHKA-00/04]** Trae、Codex、CodeBuddy等属于**开发与工程维护平台（CTX-ENG）**，不是普通人每创作一件作品必经的产品流程。外部AI模型/Provider是产品运行时可授权调用的执行能力；开发平台以后仍可用于修复、接入新工具和系统升级，但不能代替墨痕自身的Studio产品能力，也不能凭工程开发权限获得史学Gate签发权。

## 5. Studio研究资产：身份、价值、积累与存储基线

### 5.1 为什么既有正式知识库，还要研究工作资产？

**[现行MHKA-03/知识资产合同]** 正式L知识回答「已有何种适用资格的历史文化知识」；Studio工作资产回答「这个问题如何提出、资料如何选择、有哪些尚未验证的分析、冲突与下一步、怎样形成作品」。工作候选有价值，但**没有独立G签发的对象不可自动升级为正式历史事实**。

**[现行合同确定的13类，不得因本讨论直接增删]** 这13个英文ID是字段 `studio.asset_heads.asset_kind` 可选的**13种业务类型值（枚举词项）**，**不是13张数据表**。类型与表名要区分：`studio.asset_heads`是一张资产身份表，`studio.asset_revisions`是一张资产修订表；不同`asset_kind`的对象通过同一结构以自身的`asset_id@revision`持久化，下游字段、权限按类型各自约束。下列三组只是**解释价值的讨论分组**，不是第二份asset_kind登记或新的数据库分类：

| 价值分组 | 现行asset_kind | 核心用途 |
| --- | --- | --- |

### 5.5 真实积累机制：以知识增量而非资产数量为准（深化建议）

**长期积累的三个目标**：材料与证据以后可精确返查；尚未证实的时空关系、反证与人文理解可以继续发展；真实创作选择和作品版本可以恢复与合法借鉴。Studio工作资产不是第二套正式L真源，也不是每段聊天都要存入的资料仓库。13类的业务身份及逐类价值仍以§5.4唯一矩阵为准。

**从实际工作触发，而不是按13个字段机械生产：**

| 业务时点 | 产生有意义资产的条件 | 不应计为新积累 |
| --- | --- | --- |
| ST-01确定问题与范围 | `research_brief`保存Creator意图、时空与成果用途的真实修订 | 每句聊天另存一个Brief；模型替作者决定选题 |
| 检索与来源发现 | `source_anchor`锁定来源版本/合法目录状态/原件定位；`research_collection`只保存跨题精确引用集合 | 没取得原文却记为取得；复制一份已有L0字节；集合批量继承资格 |
| D01阅读与校勘 | `reading_note`保存新的页区疑字、可重演方法/误读限制 | 把正式L1整篇复制成第二套主本 |
| D02证据对照 | `evidence_note`记录实际原文、转引/同源、观察与反证增量 | 模型摘要称为原件；同一转引算独立多来源 |
| D03世界构建候选 | `spacetime_candidate`、`relation_hypothesis`记录可查时地/关系、替代解释和反证 | 现代坐标直接充作古城位置、相邻等于联系 |
| D04人文发现候选 | `humanistic_insight`记录比较方法、具体的当下联系、认识增量与不确定性 | 换修辞、空泛赞叹或无依据感想算新发现 |
| H1/H2/H3与投稿 | `director_plan/media_selection/work_revision/citation_snapshot`封套锁定实际导演取舍、合法媒资、作品主本修订和引用时点 | 新建第二份导演/媒资/作品正文，预览成功当发布 |
| 自愿贡献 | `consented_feedback`保存明确同意、具体观察和可撤回约束 | 用浏览、点击、停留擅自生成用户知识贡献 |

**每份长期资产最低必须可答**：归属Project/Actor/受托来源、稳定`asset_id@revision`及hash、具体价值及认识类别、精确source/L/依赖和定位、支持/反证及缺口、当前权限/权利/状态、是否真实被复用及其`use_event`；外部AI参与要有实际Provider/工具和Receipt。只知道目录时诚实记录目录状态，不造原件页码或引文。未经核实的私有研究可以留`WORKING/UNASSESSED`；只有必要的授权、来源/依赖和新鲜度验证之后才可判断研究复用就绪。**事务记录和失败回执即使没有知识增量也应按合同保存，但不计为新历史认识。**

**唯一存储关系不改**：`studio.projects → studio.asset_heads + studio.asset_revisions → studio.asset_links/use_events`，受托执行对应`studio.delegations/execution_receipts`；正式L知识、导演、媒资和作品正文仍由原各自的Canonical主本持有。PostgreSQL保存版本与关系，私有对象存储保存真实原件/大文件，可重建索引不承载独立Truth。

### 5.6 真实复用机制：找到、获权、使用、形成差异

1. **明确目标**：当前Project、Actor、问题、用途/consumer、动作（研究读取/引用/展示/外发）、预算与必要权限。
2. **优先查询合法旧知识**：正式`L@rev`和Studio`asset@rev`分别返回精确修订及“已资格化/工作候选/受限”等认识身份；未授权内容不能通过搜索摘要泄露。
3. **执行当前校验**：源身份、locator、依赖闭包、修订、项目ACL、同意、rights与对应Gate的当前适用性。旧许可/快照不自动延续；缺关键前提则HOLD，不允许用缓存复活。
4. **选择三种路径**：①无需变更的精确引用；②同项目有新证据/理解时建立原资产新revision或合法关联；③跨项目有独立授权时引用或Fork为B项目工作资产，保留A来源与修订，而非复制原件或继承A的权限。
5. **真实执行后记账**：实际引用/读取成功后才生成`use_event`，记录actor、consumer、purpose、action、rights_decision和旧rev；搜索命中、计划或被拒绝的尝试不能计为已复用。
6. **证明增长并维护失效**：新项目记录旧A修订、B新成果的精确修订、至少一个有据的新来源/读取/关系/解释或反证、与旧成果的差异；源/权利/G变更时先阻断受影响消费，再定向重审，旧合法审计保留。

| 复用结果 | 可被证实的价值 | 不能偷换的结论 |
| --- | --- | --- |
| 有权引用旧原件/证据或正式L | 少走重复查找、读取与定位步骤；具体时间收益以后实测 | 引用次数≠新增史学发现；旧G≠当前合法 |
| 有权承接旧研究假说或问题 | 能从旧证据/反证继续调查，不必重新提出相同问题 | `REUSE_READY`≠G3/G4，跨项目权限不自动继承 |
| 新题产生新依据/观点/反证 | 可说明具体知识增量与旧认识的变化 | 更换标题或生成新摘要≠知识增长 |
| 复用已有导演结构/素材线索 | 改善创作连续性和可恢复性 | 创作复用≠媒体展示许可、史学资格或可发布性 |

**面向用户的最终结果**应让Agent说清楚：「这次复用了上一次研究的哪份来源、哪段证据、哪条未决问题；本次新找到了什么、修正了什么、还缺什么。」不应只报告“13类资产增加了几条”。

### 5.7 Studio研究资产进入正式D/L/G的精确规则

申请正式知识时，提交的是**具体有据候选与真实上游**，不是将整份研究工作资产批量盖“G合格”章。通过受控`RequestFormalProduction(asset@rev)`产生`Studio候选@rev → 正式生产请求 → 对应L@rev与独立G决定`，原Studio历史修订不改写。若已有合法合格上游，可按用途直接引用；缺失则补相应D阶段，不能靠asset_kind跳过前置资格。

| Studio候选 | 指向的正式专业阶段 | 主要前置条件及HOLD处理 |
| --- | --- | --- |
| `source_anchor`：新来源或原件 | D00→L0/G0 | 来源/版本、真实取得状态、合法权利、必要原件字节/hash/locator；目录不冒已取得原件 |
