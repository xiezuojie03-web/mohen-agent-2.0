# RECON-01 · 图片要不要「默认不能用」

## 改什么

**现状**：图片表**没有"状态"字段**，靠一张**"排除名单"**表达不合格——**名单里没有 = 可用**。

改法三选一（我建议 **方案 A**）：

**方案 A**（建议）：给图片表加一个「状态」字段，**默认＝待审**（新图片不能自动可用）。
- 具体三处：① 加字段（默认"待审"）；② 加一条规则——标记"可用"时必须已有门禁记录；③ 把下游"有效图片"视图的判定从"没被排除"改成"状态 = 可用"。
- **不改**：现有"排除名单"字段与其取值保留；**不删任何行**。

**方案 B**：不加字段。继续用现有"排除名单"，只要求写入时**必须显式打"待审"标记**。
- 代价最小、无需迁移；但**默认仍然是"可用"**——忘了打标记的代码路径照样让未审图片变成可用。

**方案 C**：什么都不做，只在状态文件里记为已知风险。

## 为什么

实测（2026-10-02，对 `mohen_dev` 只读查询）：

| 事实 | 实测值 |
|---|---|
| 图片表有无"状态"字段 | **没有**；只有一张"排除名单" |
| "排除名单"为空的行（＝未排除＝可用） | **1220 / 1288** |
| 图片表上的自动校验规则 | **0 条** |
| 真正"有效可用"的图片 | **8 张（0.62%）** |
| 夜跑期间的门禁记录 | **0 条**（1246 张夜跑图片均无） |

**机制**：没有"状态"字段 → 表达"不合格"只能往"排除名单"加标记 → 而那两条导入脚本的写入语句**根本不带这个名单** → 落入默认空名单 → **无条件可用**。

**已发生的后果**：20 张被人工作废的图片（其中 19 张是"金泽**火车站**"的高铁列车照）被重新导入成"未排除"；341/519 张图与金泽无关；30 条根本不是图片（古籍扫描件、视频）却标成图片；727 张图的来源被挂到一个"诗词"资料上。

**不改的代价**：**默认值站在错误的一边**。任何忘记查名单的新代码，都会把没审过的图片当成可用。

## 影响谁

| 受谁影响 | 会怎样 |
|---|---|
| 「有效图片」视图 | 判定口径由"没被排除"变成"状态 = 可用" |
| 直接读图片表的脚本 | 共 **9 处**（证据回收 2、视觉链接 1、体验构建 1、审计与报表 3、夜跑去重 2）——**都不在体验运行时路径上**，见下节 |
| 图片表全部 1288 行 | 会被统一置为"待审"（**不删除**） |
| **体验本身是否受影响** | **不受影响**——前端不读数据库，读的是已生成的体验 JSON |

## 我已查清（不需要你回答）

以下三项原本被我写成了问题，实际都是**工程判断**，已自行处理：

1. **有没有代码绕过视图直接取图？** 有 9 处脚本直接读图片表，**但前端（`apps/web`）完全没有**——它读的是 `apps/web/data/experience/*.json` 这类已生成的体验数据。所以本改动**不会让体验少掉图片**。
2. **会不会把现在有效的 8 张也变成"不可用"？** **按原提案的字面写法会——而且这正是此前发生过一次的事故**（`TASK-0008-result.md` 记录过"有效图片由 8 归零"）。**已修正迁移写法**：迁移时把有"确认链接 + 证据"的那 8 张直接置为"可用"，其余置"待审"。
3. **要不要分步做？** **已决定分两步**：第一步只加字段与规则（**行为不变**，可随时撤销）；观察一轮后再做第二步（改视图判定口径）——第二步才是真正改变"可用"含义的那步。

## 怎么回滚

- **第一步**：字段与规则可直接删除（两行 SQL），**行为无变化**。
- **第二步**：视图可 `CREATE OR REPLACE` 回原定义（原定义在迁移历史中）。
- **数据**：置为"待审"不丢信息——原状态可由"排除名单"重建，**无需单独备份**。
- **整个过程不删除任何行。**
