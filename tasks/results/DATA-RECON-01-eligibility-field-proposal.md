# RECON-01 · 图片要不要「默认不能用」

## 改什么

**先解释一个词**：下面说的「**加一个字段**」，就是**给图片表多加一列**，跟 Excel 加一列一样。

**现在的图片表**（一行 = 一张图，只列关键几列）：

| 图片 ID | 文件地址 | 权利 | **排除名单** |
|---|---|---|---|
| a1 | …fangshengqiao.jpg | CC BY 4.0 | （空） |
| a2 | …CRH380B-3762.jpg | CC BY-SA 4.0 | `excluded_from_heritage_primary` |

→ **"排除名单"是空的 = 可用**。所以 a1 **自动就是可用素材，没人审过它**。要让它不可用，只能事后往"排除名单"里加一笔。

**加了「状态」列之后**：

| 图片 ID | 文件地址 | 权利 | 排除名单 | **状态** |
|---|---|---|---|---|
| a1 | …fangshengqiao.jpg | CC BY 4.0 | （空） | **待审** |
| a2 | …CRH380B-3762.jpg | CC BY-SA 4.0 | `excluded_…` | **已排除** |

→ 新图默认是**待审**；只有被明确标成「可用」的，才进"有效图片"。

四种做法：

**方案 A**（建议）：加上面那张表里的「状态」列，**默认 = 待审**。
- 具体三处：① 加列；② 加一条规则——标"可用"时必须已有门禁记录；③ 把"有效图片"的判定从"没被排除"改成"状态 = 可用"。
- **不改**：现有"排除名单"列与取值保留；**不删任何行**。

**方案 B**：不加列。继续用"排除名单"，只要求写入时**必须显式打"待审"标记**。
- 代价最小、无需迁移；但**默认仍然是"可用"**——忘了打标记的代码路径照样让未审图片变成可用。

**方案 C**：什么都不做，只在状态文件里记为已知风险。

**方案 D**：**这件事不问你**，由开发平台依宪法既有原则直接实施，事后向你报告结果。
- 依据：宪法 **C3 §4.1／§4.2** 本来就规定"数据必须过门禁才能进入可用状态"，而库里**没有这个机制** → 这属于**宪法与实现之间的缺口，不是新政策**；**C3 §478** 明确这类"既有契约内的修复"**开发平台可直接实施**。
- 代价：图片的默认语义会变（新图不再自动可用），但**你不会事先看到**。

## 为什么

实测（2026-10-02，对 `mohen_dev` 只读查询）：

| 事实 | 实测值 |
|---|---|
| 图片表有无「状态」列 | **没有**；只有"排除名单" |
| "排除名单"为空的行（＝未排除＝可用） | **1220 / 1288** |
| 图片表上的自动校验规则 | **0 条** |
| 真正"有效可用"的图片 | **8 张（0.62%）** |
| 夜跑期间的门禁记录 | **0 条**（1246 张夜跑图片均无） |

**机制**：没有「状态」列 → 表达"不合格"只能往"排除名单"加一笔 → 而那两条导入脚本的写入语句**根本不带这一列** → 落入默认空名单 → **无条件可用**。

**已发生的后果**：20 张被人工作废的图片（其中 19 张是"金泽**火车站**"的高铁列车照）被重新导入成"未排除"；341/519 张图与金泽无关；30 条根本不是图片（古籍扫描件、视频）却标成图片。

**不改的代价**：**默认值站在错误的一边**。任何忘记查名单的新代码，都会把没审过的图片当成可用。

## 影响谁

| 受谁影响 | 会怎样 |
|---|---|
| 「有效图片」的判定 | 由"没被排除"变成"状态 = 可用" |
| 直接读图片表的脚本 | 共 **9 处**（证据回收 2、视觉链接 1、体验构建 1、审计与报表 3、夜跑去重 2）——**都不在体验运行时路径上** |
| 图片表全部 1288 行 | 会被统一置为"待审"（**不删除**） |
| **体验本身** | **不受影响**——前端不读数据库，读的是已生成的体验 JSON |

## 我已查清（不需要你回答）

1. **有没有代码绕过"有效图片"的判定直接取图？** 有 9 处脚本直接读图片表，**但前端（`apps/web`）完全没有**——它读的是已生成的体验 JSON。本改动**不会让体验少掉图片**。
2. **会不会把现在有效的 8 张也变成"不可用"？** **按原写法的确会——而且这正是此前发生过一次的事故**（`TASK-0008-result.md` 记过"有效图片由 8 归零"）。**已修正**：迁移时把有"确认链接 + 证据"的那 8 张直接置为「可用」。
3. **要不要分步做？** **已决定分两步**：第一步只加列与规则（**行为不变**，可随时撤销）；观察一轮后再做第二步（改"可用"的判定）——第二步才真正改变"可用"的含义。

## 怎么回滚

- **第一步**：列与规则可直接删除（两行 SQL），**行为无变化**。
- **第二步**：判定条件可改回原样（原写法在迁移历史中）。
- **数据**：置为"待审"不丢信息——原状态可由"排除名单"重建，**无需单独备份**。
- **整个过程不删除任何行。**
