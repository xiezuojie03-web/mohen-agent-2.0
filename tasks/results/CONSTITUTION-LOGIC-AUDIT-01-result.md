## 二、#1 问题结论（已采纳的层级路径标准）

用户确认的一级宪法层级与路由路径如下，据此 #1（C0–C4 内部仲裁缺失）的解决方案确定为本路径：

```
CODEBUDDY.md（纯路由，新任务读取的第一份文件）
   └→ CURRENT.md（职责：说明当前状态，Live SOT）
   └→ C0（职责：角色 / 治理 / 开发逻辑，含提交确认机制、开发协议五步）
        └→ C1（职责：方向 / 冻结原则，规划产品理念与方向）
             └→ C2（管代码和工具）/ C3（管数据库）/ C4（管 UI）
                 （各自专业域更高细节 Authority，但不得反向改写 C1）
```

**确定的优先级与职责边界**：
- CODEBUDDY：纯入口路由，**不承载任何宪法/状态内容**；新会话第一读取文件。
- CURRENT：当前状态（Live SOT）。
- C0：角色 / 治理 / 开发逻辑（含提交确认机制、开发协议五步）。
- C1：方向 / 冻结原则（Final Vision、Product Promise、Evolution Horizons、长期冻结原则）。
- C2 / C3 / C4：各自专业域更高细节 Authority，但不得反向改写 C1 的方向 / 冻结原则。

**仲裁规则**：C0（治理）≥ C1（方向）> C2/C3/C4（专业域，域内优先但不越 C1）。专业分册与总纲边界交叉时，以 C1 的方向/冻结原则为上位，专业分册仅在其域内细化。

## 四、修订后实施顺序建议

**排序原则**：治理正确性（层级 / 协议 / 职责矛盾，直接影响开发逻辑是否正确）优先于维护一致性（符号 / 版本等不破坏逻辑但易漂移的项）。本顺序与「三、重新评估」的修正归类一致：#2/#3/#4/#7/#8 属治理正确性，#5/#6 属维护项。

### 阶段一 · 治理架构落地（正确性优先）
1. **#1（已采纳 · 基座）**：落实分层路径与仲裁规则（CODEBUDDY=纯路由；CURRENT=状态；C0=治理/开发逻辑；C1=方向/冻结原则；C2–C4=专业域且不得反向改写 C1）。这是 #2–#8 全部修正的层级基座。
2. **#3**：CODEBUDDY 退为纯路由，删除 §2 五步协议，仅留路由指向 C0 §7（根除入口与宪法矛盾，落实"纯路由"定位）。
3. **#2**：升级触发器按职责分层——C0 管通用治理级、C1 管方向/冻结原则级、C2–C4 仅专业域，互不重复，且专业域不越 C1。
4. **#4**：补全 C0 五步第5步对"改变 C0 自身原则/Contract"的升级路径（消除 C0 内部自矛盾）。
5. **#7**：C1 Part IV 当前状态章节（§17–§20）整体归位 CURRENT（职责归位：C1=方向，CURRENT=状态，消除重叠）。

### 阶段二 · 维护一致性（治理框架稳定后）
7. **#5**：全仓统一 `C0–C4`（en-dash），同步 CURRENT 第8/216/232 行；明确 CURRENT 状态入口口径（Authority 低于 C0–C4）。
