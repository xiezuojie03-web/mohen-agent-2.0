## 一、核心结论（先给 Owner 看）

1. **不是"选一家模型"能解决**（任务书第九节已点明）。63 方法跨三层 AI 能力，需**分级组合**：
   - **感知层（D01）**：OCR + ASR + 视觉理解 —— 专用模型，建议**本地开源**（PaddleOCR / Whisper），几乎零 API 成本；
   - **认知层（D02/D03/D04）**：LLM 分级 —— **这才是"装 AI 大脑"的主战场和成本大头**；
   - **发布层（D05）**：8 方法里 **6 个可规则化**（P01/P02/P03/P06/P07/P08 用确定性代码实现，无需 LLM），仅 **P04 有界解释组合**需要 LLM 做表述组合。
2. **成本大头在 D02–D04 的 LLM 调用**；D01 感知层走本地开源（零 API 费）；D05 几乎零 LLM 成本。
3. **推荐选型（待 Owner 拍板）**：
   - D02 材料观察 → **中档 LLM**（GLM-5 或 DeepSeek-V4-Flash），1M 上下文吃长史料；
   - D03 世界建构 → **高档推理 LLM**（DeepSeek-V4-Pro 或 GLM-5.2），强结构化 JSON 抽取 + 逻辑推理；
   - D04 人文发现 → **旗舰推理 LLM**（DeepSeek-V4-Pro 或 GLM-5.2），最强推理；
   - D01 感知 → 本地开源（PaddleOCR-VL + Whisper v4）+ 可选云端视觉（Qwen-VL / GLM-4V）；
   - D05 发布 → 规则引擎 + 轻量 LLM（P04）。

## 二、任务画像：63 方法 → 模型能力映射

### D01 感知层（C01–C08）关键技术路线（据 standards d01 原文）
- 标准明确"**原生结构抽取 > 保真格式转换 > 识别式恢复 > 视觉/语言模型候选**"——**尽量不用生成式 LLM**。
- C01 数字文本 → Python/XML 解析（lxml/Tika），确定性，零 LLM；
- C02 扫描书影 → OCR（PaddleOCR-VL / Qianfan-OCR）；
- C03 历史舆图 → GDAL/OpenCV/OCR，确定性 + OCR；
- C04 照片插图 → 视觉理解模型（Qwen-VL / GLM-4V）+ 人工复核；
- C05 结构化数据 → CSV/JSON 解析，确定性，零 LLM；
- C06 音频 → ASR（Whisper v4）+ 人工复听；
- C07 视频 → FFmpeg/PySceneDetect，确定性 + 音轨 ASR；
- C08 实物现场 → GNSS/QGIS，确定性，零 LLM。

### D05 发布层（P01–P08）技术路线（据 standards d05 原文）
- **可规则化（确定性代码，无需 LLM）**：P01 资格选入（依赖/权利检查）、P03 时空变换（坐标精度转换）、P06 证据返还（指针映射）、P07 消费分面（分面构造）、P08 精准失效（已落地 `computePreciseInvalidation`）；
- **P02 世界投影**：无增事实投影，基本规则化，可留轻量 LLM 做表述；
- **P04 有界解释组合**：需 LLM 组合 G4 解释候选 → story_seeds / agent_contexts（**唯一明确需 LLM 的发布方法**）；
- **P05 探索关系编排**：图算法 + 规则化为主，可留轻量 LLM 做路线叙述。

## 七、模型调用浪费评估（新增维度 1）

> 问题：现在生产链方法标准在调用模型上是否存在浪费？

### 7.1 结论：标准层面是"防浪费"设计，浪费风险在实现层

63 方法标准**本身多处显式防浪费**，但落地实现时有 3 个容易踩的浪费陷阱。

### 7.2 标准里已有的防浪费设计（原文依据）

| 阶段 | 防浪费设计 | 依据 |
|---|---|---|
| D01 | "原生结构抽取 > 保真格式转换 > 识别式恢复 > 视觉/语言模型候选"——能用确定性工具就不用生成式 LLM；"若原生读取已经保真，禁止无故转成模型生成文本" | d01 规范 |
| D02 | 25 个 H 方法按"精确匹配载体/材料类"选路，不广播全部方法 | method-binding-contract `selection_policy` |
| D03 | W01–W10 是**循环协同**（"相互调用，而非线性十关"），"定向重开有关 W 项，不必全部从 W01 重做"；"一个研究单元以世界主张为中心，不以 W 编号顺序为中心" | d03 规范 §2 |
| D04 | A01–A12"按问题选择，可并行、组合和回退，**不按编号强制执行**"；"理解价值筛选"是共同关口 | d04 主规 §3 |
| D05 | 8 方法里 6 个可规则化（P01/P02/P03/P06/P07/P08），只有 P04 明确需 LLM | d05 规范 |

### 7.3 三个实现层浪费陷阱（必须规避）

1. **"L2 落点缺失 → 架构断环"的风险**（根因是 L2 字段未落地，属架构缺陷，非设计意图）。标准设计上 D03 消费 L2 结构化产物，"不需读 L1 全文即可获得引文短片段、结构位置、来源限定与依赖信息"（L2 契约 §8 原文）。但 H 规范要求的 L2 结构化字段（`material_mentions` 字面提及、`assertion_kind` 断言类型、`reading_units` 结构单元、`reading_unit_dependencies` 依赖链）**当前真实库 `material_evidence` 尚未落地**（仍是旧 19 列）。若 D02 按旧表落地，中间结果落不了库，一环扣一环就会断裂。**正确修复是补全 L2 落点（字段级改库），禁止让 D03 越界回读原文替 D02 补活。** 详见 SAMPLE-TRIAL-03。
2. **方法误实现为"逐法独立调用 LLM"**。若把 W01–W10 各跑一次 LLM、A01–A12 各跑一次 LLM、H01–H25 各跑一次 LLM，一次研究单元会从 1–2 次调用膨胀到 10–25 次。标准明确"循环/按需"，实现原则应是**"一次 LLM 调用产出结构化多字段"**（W 十法的 identity/time/space/event/relation/change/claim/source/conflict/consistency 一次性 JSON 输出），再用规则后处理分发。
3. **该规则化的用了 LLM**。D01 的 C01/C05/C07/C08 与 D05 的 P01/P02/P03/P06/P07/P08 都可用确定性代码，若误接 LLM 则纯浪费。

### 7.4 落地约束建议
- 每阶段 adapter 注入时，强制"输入=上一阶段合格产物引用（非原文）"，原文只在 D02 首次喂一次。
- D03/D04 采用"一次调用产出多方法字段"的合并抽取，禁止一法一调。
- 建立 token 用量埋点，D02/D03/D04 单条全链 token 超出预算（如 >50K）即告警复核。

## 八、UI 展示效果评估与成本平衡（新增维度 2）

> 问题：生产链方法标准产出在最终 UI 展示上能实现的效果能评估吗？结合成本平衡给评估。

### 8.1 结论：能评估，且评估分两层；成本平衡结论是"先规则化骨架、后 LLM 内容"

read_model 六表 → UI 组件的映射是确定性的（可逐字段核对），效果质量则需 Owner 主观验收。结合成本，存在清晰的"低成本高可见 → 高成本高价值"梯度。

### 8.2 六表 → UI 效果 → 成本 映射

| L5 成果 | 字段特征（已核真实库） | 对应 UI 效果（金泽 water-net） | 主要方法 | LLM 成本 |
|---|---|---|---|---|
| world_projections | `payload` + `expression_rule` | 关系空间 / 冲突并列（RelationalSpace / ConflictCompare） | P02 | **低**（P02 规则化投影） |
| map_timeline_projections | `payload` + `derived_from_world_objects` | 地图 / 时间轴（CurrentMap / Timeline） | P03 | **低**（P03 规则化） |
| evidence_pointers | `display_locator` + `display_excerpt` | 证据按需揭示（EvidenceReveal） | P06 | **低**（P06 规则化） |
| story_seeds | `title` + `narrative_question` + `payload` | 主发现 / 叙事（Discovery） | P04 | **中**（LLM 组合） |
| agent_contexts | `context_key` + `payload` | AskBar 追问回答 | P04+P07 | **中**（LLM 组合） |
| discovery_paths | `path_key` + `steps` | 探索路径编排 | P05 | **中低**（图算法为主） |

### 8.3 成本平衡评估（三档）

| 档 | 内容 | 方法 | LLM 成本 | 可见性 | 建议 |
|---|---|---|---|---|---|
| 骨架层 | 世界投影 / 时空投影 / 证据指针 | P01+P02+P03+P06+P07 | ≈0（规则化） | 立刻让 UI 显示"世界长什么样、时空在哪、证据在哪" | **优先做**（性价比最高） |
| 内容层 | 故事种子 / Agent 上下文 | P04 | 单条 ≈¥0.24–0.36 | "有内容可讲"的核心价值 | **重点投入**（成本集中但价值核心） |
| 增强层 | 探索路径 | P05 | 图算法 + 轻量 LLM | 引导式探索体验 | 可后置 |

### 8.4 关键前提（结合评估 B）
- **没有 UI 通道，LLM 产出也是空转**。评估 B 已发现：金泽 water-net 视觉舞台目前只读 5 个冻结 JSON、不读 read_model（缺口 P1），API 缺 `visual_stage` 分面（缺口 P2）。因此"骨架层"落地（P02/P03 规则化）必须与"UI 通道补强"同步，否则即使 read_model 有产出，前端也看不到。
- **成本平衡的总判断**：首轮样板试验建议按 **骨架层（零 LLM 成本）→ 内容层（LLM 成本集中）→ 增强层** 的顺序推进。骨架层先行能让 Owner 尽早在前端 UI 看到效果（验证管道 + UI 通道），再投入 LLM 成本做"有内容可讲"的故事与发现，避免"先砸钱算 LLM、前端却看不见"的浪费。

### 8.5 效果评估口径（供 Owner）
- **技术可展示性**（确定性，AI 可验收）：read_model 六表字段 → UI 组件映射是否通、payload 能否被组件解析、`visual_stage` 分面端点是否接通。
- **效果质量**（主观，Owner 验收）：故事是否有"非平庸理解增量"、发现是否"有内容可讲"、证据是否可回指原文。这是 D04 的"理解价值筛选"门槛，最终由 Owner 在前端 UI 终验。

## 九、补充分析（回应 Owner 三个疑问，2026-10-17）

### 9.1 疑问 1：分层落库后，真的还会"全链重读"吗？

**结论：设计上不存在"全链重读全文"，但存在一个"设计-实现鸿沟"——若 L2 结构化字段不落地，D03 会被迫回读。**

标准原文已经明确（L2 契约 §8 末句）："**D03 不需读 L1 全文即可获得经过 G2 授权的引文短片段、结构位置、来源限定与依赖信息。**"

也就是说，设计意图是：D01 读载体 → L1 落库；D02 读 L1 观察 → **L2 落库（引文短片段 + 字面提及 + 依赖链）**；D03 只消费 L2 的**结构化中间结果**，不回读原文。

**但真实库现状与这个意图有一个缺口**（这是关键）：

| H 规范要求落库的字段 | 真实库 `material_evidence` 现状 |
|---|---|
| `material_mentions`（字面提及：人/时/地/物/数） | **未建表**（L2 契约 §7.2 列为"必须新增逻辑实体"） |
| `assertion_kind`（记述/规范/愿望/传闻/论辩…） | **未加列**（契约 §7.2 列为"建议补充"） |
| `reading_units`（作品内卷篇/条目/图幅结构单元） | **未建表** |
| `reading_unit_dependencies`（引书/转录/编辑依赖） | **未建表** |
| `quote_review_status`（引文核对方式） | **未加列** |

真实库 `material_evidence` 当前是**旧 19 列**（evidence_id/source_id/…/normalized_text/research_proposition/maturity 等），上面这些"让 D03 免回读"的结构化字段**还没落地**。

**后果（更正表述）**：如果 D02 落地时只按旧 19 列写，D02 的结构化观察**落不了库**，一环扣一环就从 L2 这里断裂。**正确的修复是补全 L2 落点（字段级改库），而不是让 D03 越界回读原文替 D02 补活——任何"下一阶段补上一阶段"都是架构退化，必须禁止。**（本处最初表述"D03 被迫回读/变相重读"不准确，已由 SAMPLE-TRIAL-03 澄清。）

**落地建议**：样板试验在 D02 落地前，先按 L2 契约 §7.2 补齐 `material_mentions` / `reading_units` / `reading_unit_dependencies` / `assertion_kind` 等字段（属"改库已授权"范围），让 D02 一次读深、产出充分结构化中间结果并落库，D03/D04 才能"消费上一层"一环扣一环。

### 9.2 疑问 2：D02 是否已做到"每类史料快速读取最有用的信息"？

**结论：H01–H25 标准"定义每类史料结构"已达标，但"快速读取"的工程化手段还有 2 处不到位。**

#### 已达标的部分（H 标准确实做了）
- 第二节索引表给**每类史料**列了"首先辨别的阅读结构"（如 H05 地方志：序跋凡例、舆图、沿革、山川、建置、人物、风俗、艺文、杂记；H07 行政档案：件号、收发机关、日期、呈文、批示、附件、套卷）；
- 每个 H 方法有"内部结构"（沿结构建层级路径）+ "领域知识与话语分层"（辨"史家编纂层/旧材料层/校注层"）+ "最小结构化产出"（该类史料最该提取的信息）。
- 这就是"每类史料有自己的结构、知道该读什么"——**这是不浪费成本的第一前提，H 标准达到了**。

#### 不到位的 2 处（真正的成本杀手）
1. **阅读动作写的是"逐句记录材料所述"，倾向全文通读，而非"结构化跳读"**。
   - 25 个 H 方法全部要求"先逐句记录材料所述，再做限定性释义"——这是"通读全文 + 逐句提取"，不是"按结构定位关键区 → 精读关键区"。
   - 一篇方志 20K token：逐句通读是全文成本；若按 H05 的"志目结构"先定位到"沿革/山川/建置"关键卷再精读，成本可能只有 1/3~1/5。
   - **标准给了"结构地图"（读哪里），但没给"读取预算/优先级"（哪些精读、哪些略读、哪些跳过）**。
2. **"最小结构化产出"是概念描述，未绑定为 JSON schema**。
   - 每个 H 方法产出字段是文字描述（"志目路径、修志年代、记载时段…"），且明说"字段为逻辑语义，物理命名归 04 决定"。
   - L2 契约 §6.1 的 28 个"最小不可缺字段"也**尚未落地成真实表结构**（见 9.1）。
   - 结果：LLM 无法按严格 schema 一次输出到位，容易输出松散文本、反复返工——**这本身就是 token 浪费**。

#### 落地方向（让 D02 真正"快读省成本"）
- 把 H 规范的"内部结构"转成**分步提示词**：① 分类（一次轻量判断）→ ② 按结构定位关键区（给出该史料的关键卷目清单）→ ③ 精读关键区 → ④ 按 JSON schema 结构化输出。
- 把"最小结构化产出"绑定为**严格 JSON schema**（含 `material_mentions` 的人/时/地/物/数结构化数组），让 LLM 一次输出、不返工。
- 原文全文只在 D02 喂一次，且可先做"章节级切分 + 关键段预筛"，非关键段（如方志"艺文"里的应酬诗文）默认略读。

### 9.3 疑问 3：本地存储/缓存应从样板试验就开始（不是规模扩大后再补）

**结论：同意，且这应是样板试验的"硬性架构基线"，不是可选项。规模路径必须现在就真实跑通。**

#### 三层"本地优先"方案（从样板试验第一天就落地）

| 层 | 方案 | 省什么 | 关键约束 |
|---|---|---|---|
| **LLM 响应缓存** | 以输入指纹（原文 hash + 提示词版本 + 模型版本）为键缓存 LLM 输出到本地 PG（或本地 KV）；命中即不调用 | 重复调用成本、延迟 | 缓存必须绑定"输入指纹/规则版本"，改提示词或换模型即失效（`material_evidence.input_fingerprint` 已为此预留语义） |
| **中间结果本地落库** | D00–D05 每层产物落本地 PG（已是分层 schema 设计），D03/D04 只消费上一层，不重算 | 重读/重算成本 | 这正是 9.1 的关键：必须先补全 L2 结构化字段，中间结果才"够用" |
| **本地向量/检索** | 若 D04 需要跨大量 L2/L3 结果检索相关上下文（RAG），用 pgvector（PG 本地扩展）存 embedding + 本地 embedding 模型 | 避免每次把全文/全库喂给 LLM | 史料原文不出域；embedding 本地算 |

#### "把规模路径真实跑出来"的具体含义
- **样板试验即用真实生产骨架**：`production-registry.json`（activation 转 true）+ 六阶段 executor + 真实 PG 落库 + `gate_audits` 追加审计，**不用临时脚本**。规模扩大时只是加数据量、加缓存容量，不换架构、不迁移。
- **缓存/指纹从第一条数据就建**：每条材料从 D00 就有 `input_fingerprint`，LLM 结果按指纹缓存，确保"换提示词/换模型/换来源版本"能精准失效重算，而不是"规模大了才发现缓存乱了"。
- **数据不出域从样板试验就确立**：史料原文 + 中间结果 + embedding 全部本地，LLM 调用只传"必要的局部引文短片段"（L2 `literal_reading`），既省 token 又满足版权/隐私。

#### 一个需要 Owner 提前拍板的关联决策
本地部署 embedding + 向量检索需要确定**向量存储选型**（pgvector 扩展 vs 独立向量库）和 **embedding 模型**（本地开源如 BGE/智源，还是云端 API）。建议样板试验用 **pgvector（复用本地 PG，零新组件）+ 本地开源 embedding**，与"本地优先"一致；此项我可并入下一步落地清单。
