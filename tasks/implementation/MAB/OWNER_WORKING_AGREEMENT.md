# Owner 工作协议（协作习惯蒸馏）

身份：协作方式说明，不是设计权威、施工计划或验收标准。与 `PLAN.md`、MHKA、专业合同冲突时一律以它们为准。
来源：Owner 在旧平台留下的工作记忆，仅保留与现行 MAB/MHKA 不冲突且经 2026-11-24 仓库核实的部分。

## 1｜决策与节奏

- 先给策略与取舍，不直接开干；改动方向、范围或代价未定时先确认方案再写码。
- 一任务一 STOP：完成、验证、汇报后停下，不自行进入下一任务；Owner 明确授权连续施工时才跨批推进。
- 长任务要分段汇报；不静默推进到结束才出现。
- 有冲突、循环或不可执行障碍时停下，报位置、原始失败、风险和最小修正建议；不暗中降低安全底线。

## 2｜交付形态

- 中文沟通、中文文档；代码注释沿用所在文件既有语言。
- 汇报固定结构：基线 SHA → 任务 → 改动/提交 → 测试与真实结果 → 阻断 → 下一步。
- 结论用编号或表格；验收用判据清单（PASS/FAIL + 证据），不用"应该/大概"。
- 数字必须实测；未验证项显式写 `NOT_RUN`/`DEFERRED_ENV`，不靠推断补齐。
- 讲用户能获得什么，而不是堆砌工作量。

## 3｜红线（现行仍有效）

- 凭据只在 gitignored 的 `.secrets/`；不打印、不截图、不提交、不写入报告。
- 不物理删除数据或文件；下线和废弃一律留痕。
- 不伪造 PASS：设计、代码、CI、隔离、线上、Owner 签收是不同证据层，本地测试不能冒充 CI 或专业 Gate。
- 不编造数据、坐标、引文；不确定就降级为缺口或待裁，原文照录不篡改。
- 不生图冒充史料；图片必须可溯源。
- 新增 UI/交互先出样稿经 Owner 确认再写代码。
- 不擅自推生产、不擅自开付费模型、不擅自扩权限。
- 外部旧仓库（`hushang-jingwei`）永久只读，不写入、不改动。

## 4｜动手顺序

调研 → 确认基线/备份 → 方案确认 → 写码 → 验证 → commit。一次只推进一个可验证批次，完成后回写证据。

## 5｜本机环境坑（2026-11-24 核实仍成立）

- 集成测试必须串行：`vitest.config.ts` 的 `fileParallelism: false` 不得改动，并行会互相污染数据库审计计数。
- 不在源码目录单文件跑 `tsc xxx.ts`：会产出 `.js` 并静默改变模块解析，造成"检查通过、代码改了、行为没变"。
- 本机 `spawnSync` 起 node 子进程有 EBUSY 历史（见 `tests/legacy/data/*.test.ts` 内注释）；子进程型测试失败先判环境，再判回归。
- `scripts/dev-skills/continuation.mjs verify --profile typecheck` 在 Windows 本机会返回 `EINVAL`（无法 spawn pnpm），属启动器限制；等价证据直接用 `pnpm -r typecheck`，并在报告注明该差异。
- `pnpm -r typecheck` 只覆盖 workspace 包，`tests/` 不在其内；补检用 `--noEmit` 并核对产出为 0。
