# 墨痕 Agent 2.0 —— 数据库架构设计 · 真源与文件映射

> 生成时间：2026-09-26 ｜ 回应问题："`data/` 是全部数据库文件吗？我要更详细的数据库架构设计及对应文件。"
> 结论先行：**`data/` 不是数据库。** 真正的数据库是本机 PostgreSQL 实例 `mohen_dev`，schema 以迁移脚本形式 git 跟踪，由唯一访问层写入、运行时只读。

---

## 一、直接回答：数据库到底是什么、在哪

| 问题 | 答案 |
|---|---|
| `data/` 是数据库吗？ | **不是**。它只是"工作/派生区"——`data/raw` 仅一个 README、`data/staging` 为空、`data/exports` 是一堆 CSV/JSON/MD 报告（产物留痕，非真源）。 |
| 真数据库在哪？ | **本机 PostgreSQL 18 实例**，库名 `mohen_dev`，地址 `127.0.0.1:5432`。物理数据文件在 PostgreSQL 的数据目录里（磁盘上，不在 git 仓库）。 |
| 仓库里"关于数据库"的文件有哪些？ | ① schema 定义：`supabase/migrations/*.sql`（git 跟踪，真源）；② 唯一访问层：`packages/data-access/src/index.mjs`；③ 写入脚本：`pipelines/*`；④ 连接配置：`.env.local`（gitignored，含 `DATABASE_URL`）；⑤ 运行时只读投影：`apps/web/data/experience/*.json`（5 份冻结 JSON，git 跟踪，体验层快照）。 |
| 怎么连？ | `DATABASE_URL=postgresql://mohen_app@127.0.0.1:5432/mohen_dev`（在 `.env.local`）。通过 **psql 二进制**驱动（`PSQL_PATH` 默认 `D:\MoHen\tools\PostgreSQL\18\bin\psql.exe`），**零 npm pg 依赖**，离线可复现。 |

> 注：`.env.example` 里写的是 `postgresql://postgres:postgres@127.0.0.1:54322/postgres`（54322 是 supabase 默认端口），那是模板，**实际库是 5432 的本地 PG 18**，以 `.env.local` 为准。

## 二、架构分层（心智模型）

```
                 外部来源（上图 API / 古籍 / Commons 图 / 人审记录）
                          │
                          ▼  ingest / extract / normalize / review / evidence / weave / visual / historical-spatial
              ┌───────────────────────────────────────────────┐
              │  pipelines/*  （确定性、只写、可重跑）            │
              └───────────────────────────────────────────────┘
                          │  唯一写入口
                          ▼
              ┌───────────────────────────────────────────────┐
              │  packages/data-access  (queryRows/run/runMany)  │  ← 全仓库唯一 DB 访问层
              └───────────────────────────────────────────────┘
                          │  psql -f 临时 SQL（:'name' 安全转义 + E'' 防反斜杠失真）
                          ▼
              ┌───────────────────────────────────────────────┐
              │  PostgreSQL  mohen_dev   ★真源（SOT）            │
              │  schema = supabase/migrations/*.sql（7 个迁移）  │
              └───────────────────────────────────────────────┘
                          │  运行时只读
                          ▼
              ┌───────────────────────────────────────────────┐
              │  apps/web/lib/mohen-agent/retrieve.ts           │  ← ②检索契约（UNION 多表）
              │  → AskBar 渲染墨痕线                              │
              └───────────────────────────────────────────────┘
                          │  另有一条"冻结投影"通道（不经 PG）
                          ▼
              apps/web/data/experience/*.json  🔒 5 份冻结 JSON（体验脚本/状态序列/文化世界切片/历史空间切片）
              → page.tsx 服务端读取 + checkFrozenInvariants 失败即 loud
```

**三层真源边界（关键，避免混淆）：**
1. **PG `mohen_dev`** = 知识库真源（实体/证据/主张/关系/文化世界/历史空间/视觉链接…全部在此）。
2. **`apps/web/data/experience/*.json`** = 体验层**只读快照**（把 PG 里金泽切片"烘焙"成前端不可变的体验脚本）。改体验必须改 PG→重烘焙→更新 JSON，且 JSON 受 `checkFrozenInvariants` 绑死。
3. **`data/`** = 临时/派生工作区，**不进真源**（重建库后可丢，不影响知识）。

## 三、逐层表清单（共 26 张表 + 1 视图 + 4 枚举 + 6 触发器）

### 层 1 · 证据底座（迁移 `001_foundation.sql`）
> 全链路根：`source → evidence → entity / claim / relation`

| 表 | 作用 | 关键列 |
|---|---|---|
| `source_records` | 来源登记（一本账） | provider / title / checksum / raw_path / metadata_json |
| `evidence` | 证据（最小可引用单元） | evidence_type / quote_text / region_json / subject_hint / place_hint / time_hint / confidence / **verification_status(8值)** |
| `entities` | 实体（桥/寺/人/镇…） | entity_type / canonical_name / aliases / valid_from / valid_to / status |
| `claims` | 主张（subject 谓词 object） | predicate / object_value / certainty / review_tier(A/B/C) / generated_by |
| `claim_evidence` | 主张↔证据 | support_type |
| `relations` | 关系边 | predicate / valid_from / valid_to / confidence |
| `relation_evidence` | 关系↔证据 | support_type |
| `visual_assets` | 视觉资产（图/地图） | asset_type / file_path / depicted_period / rights / quality_score / **eligibility_tags**(003追加) |
| — 触发器 | `guard_published_claim_evidence` | **published 的 claim 必须有证据**，否则拒绝写入 |

### 层 2 · 数据工厂 / 审计（迁移 `002_data_factory.sql`）
| 表 | 作用 |
|---|---|
| `ingest_runs` | 每次摄取运行的审计（输入/候选/验证/拒绝计数） |
| `review_queue` | 复核队列（Tier A/B/C） |
| `legacy_mappings` | 旧系统（Legacy）ID → 新实体映射 |
| `evidence_gate_audit` | 证据门禁 **G0–G6** 逐关审计（来源完整/对象身份/时间语义/空间诚实/证据支持/冲突检测/发布资格） |
| — 触发器 | `guard_review_queue_tier_c` | **Tier C 不得自动 approved**，必须有人审 note + 时间 |

### 层 3 · 人工复核决策（迁移 `003_human_review.sql`）
| 表 | 作用 |
|---|---|
| `human_review_decisions` | HR-1~HR-6 人审决策落库（hr_code / decision_code / object_ref / review_note / actor=human / status_after / machine_readable_flags）。**与 review_queue 的 Tier A/B/C 语义不同，单列不混用** |
| — 追加列 | `visual_assets.eligibility_tags`（落实 HR-5：20 张资产不得进 heritage-primary） |

### 层 4 · 知识编织（迁移 `004_knowledge_weave.sql`）
| 表 | 作用 |
|---|---|
| `knowledge_paths` | 机器可读有序 claim/relation/change 链（purpose_question / evidence_coverage / **unresolved_breaks 必须显式声明断裂**） |
| `knowledge_path_steps` | 路径步骤（entity/claim/relation/change） |
| `discovery_candidates` | 发现候选（必须带 objects + relationship_change + evidence_refs + relevance_question + humanistic_why） |
| — 触发器 | `guard_weave_not_publishable` | **Knowledge Weave 产物不得 publishable=true** |

### 层 5 · 视觉链接（迁移 `006_visual_linkage.sql`）
| 表 / 视图 | 作用 |
|---|---|
| `visual_entity_links` | 图↔实体链接表（link_status: confirmed/suspected/similar/unconfirmed；current_or_historical；link_evidence_id） |
| `effective_visual_assets` | **视图**：confirmed + 双方均未被 HR-5 排除 = 唯一计入口径（防各脚本 SQL 漂移） |
| — 触发器 | `guard_confirmed_link_has_evidence`（confirmed 必须有证据）；`guard_excluded_asset_not_heritage_confirmed`（HR-5 排除资产不得 confirmed） |

### 层 6 · 历史空间重建（迁移 `007_historical_spatial_reconstruction.sql`）
> 刻意**不建任何 geometry 列**（坐标原值 + 显式 coord_system），历史几何一律 unknown，禁 AI 补画。

| 表 | 作用 |
|---|---|
| `historical_spatial_slices` | 切片头（focus_question / spatial_extent_current / historical_geometry_status / uncertainties / readiness_gate） |
| `historical_features` | 历史特征（feature_key / canonical_label / geometry_type / attested_time_* / **historical_position_status vs current_position_status 必须分开** / change_status） |
| `historical_feature_anchors` | 空间锚（**有坐标就必须有 CRS**，当前 provider 锚点永远不得声明为历史位置证明——库层强制） |
| `historical_change_records` | 逐条变更断言（evidenced/candidate/unknown；evidenced 必须真带证据） |
| `historical_spatial_relations` | 切片关系（**E1–E4 知识级别**，复用 relations 但不改它） |
| — 枚举 | `historical_geometry_type`(point/line/area/unknown) / `historical_spatial_status`(6值) / `historical_change_status`(8值) / `historical_relation_class`(E1/E2/E3/E4) |

### 层 7 · 文化世界对象（迁移 `008_cultural_world_objects.sql`）★ 运行时主读层
| 表 | 作用 |
|---|---|
| `cultural_events` | 事件（事实层；epistemic_status **6值**：SUPPORTED/SUPPORTED_CANDIDATE/CONFLICTED/RESEARCH_LEAD/UNSUPPORTED/OPEN_QUESTION） |
| `cultural_relation_claims` | 关系主张（FACT/RELATION；evidence_fragment_ids 精确到片段；spatial_scope 不得用今天坐标代历史位置） |
| `cultural_meaning_candidates` | 意义候选（**仅基于已支持 Claims**，INTERPRETIVE 语气，不升为 Fact） |
| `cultural_present_connections` | 今址/复建双层观察（site_vs_rebuilt / today_location / ruins_reconstruction） |
| `evidence_fragments` | 证据片段（AD-05：最小放行单位不是整条 Evidence，Claim 精确引用可用 fragment） |
| `cultural_conflicts` | **结构化冲突保存**（1265 vs 1267 互相定位，resolution_status='preserved_open'，不抹平） |

> 迁移序号说明：`005` 被**有意跳过**（008 注释明令"禁止回填 005"）。已提交迁移为 `001,002,003,004,006,007,008` 共 7 个。

## 五、关键设计纪律（库层强制，不是口头约定）

1. **几何本身即主张**：`historical_feature_anchors` 不建 geometry 列；有坐标必须有 `coord_system`，当前 provider 锚点永远不得 `historical_position_proof`。
2. **published 必须有证据**：`claims` 触发器拦截无证据的发布。
3. **Tier C 必须人工**：`review_queue` 触发器拦自动 approved。
4. **confirmed 视觉链接必须有证据**：`visual_entity_links` 触发器 + `effective_visual_assets` 视图是唯一口径。
5. **Knowledge Weave 不可发布**：`discovery_candidates.publishable` 强制 false。
6. **冲突结构化保存不抹平**：`cultural_conflicts` 双向定位，`preserved_open`。
7. **E1–E3 关系必须有证据链**，E4 允许空（合理但证据不足）。
8. **反斜杠修复（TASK-0008）**：`data-access` 渲染 SQL 必加 `E''` 前缀，避免 PG18 `standard_conforming_strings=on` 下 JSON/路径静默失真。

## 六、风险 / 待确认点

- ⚠️ **库不在仓库内**：`mohen_dev` 是本地 PG 实例，磁盘数据目录未纳入 git。若换机/重装，需靠 `supabase/migrations/*.sql` + `pipelines/*` 重烘焙（数据本身需单独备份，当前无备份脚本明示）。
- ⚠️ **`packages/ui` 名实不符**（旧结论）：空壳，真实 UI 在 `apps/web`。
- ⚠️ **冻结 JSON 与 PG 双通道**：体验层读 JSON、知识层读 PG，二者靠"重烘焙"同步，存在漂移风险（改 PG 后须重烘焙并更新 JSON，否则体验层看不到新数据）。
- ⚠️ **`data/` 易被误当数据库**：已在本文档澄清，建议后续在 `data/README` 写明"非真源"。
