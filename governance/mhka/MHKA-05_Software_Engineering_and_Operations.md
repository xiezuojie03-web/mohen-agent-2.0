# MHKA-05｜墨痕工程实现与运行架构章程

**当前身份**：`ENGINEERING_DESIGN_AUTHORITY_ACTIVE / RUNTIME_NOT_ATTESTED` · 原 K2 设计稿 V0.1（2026-10-30），经 Owner 2026-11-05 施工权威裁决采用并受控补充  
**工程路径**：`governance/mhka/MHKA-05_Software_Engineering_and_Operations.md`（已纳入 GitHub main 新架构施工入口；2026-11-02 KAD6/MAB 交付包仍作为冻结的设计来源快照，不自动扩大运行资格）  
**唯一职责**：如何把 MHKA-01—04 的价值、产品、知识和 Agent 专业能力转成可靠的软件结构、持久化、权限、API、测试、部署、运行、安全与长期维护机制。  
**不定义**：用户产品行为的意义、历史事实及 G 资格本义、专业方法算法、Owner 架构决策权。具体 SQL/API/Schema/Registry 机器字段由 K3 已授权的现行专业合同及后续受控修订承担，本章不是工程实施的现成命令清单。

## 1｜工程服务产品：可观察、可追溯、可替换

**工程资产现实基线：** 固定 GitHub 提交已存在 `pipelines/data-production` 六阶段生产链、`packages/data-access` 双后端及六类读模型、`agent-runtime`／`experience-engine`、Studio/运营/WATCH/EXP接口、测试和迁移。工程目标是继承现有实现、补齐五图和治理缺口，不是建设另一个新的执行平台；新增技术模块须具备旧实现复用/隔离/迁移/回滚分析。

工程不是“把旧数据工作台前面贴一套新 UI”，也不是每次创作都要工程师修改源码。工程的首要目标是长期、稳定地承接自然语言研究、数据生产、作品创作、知识资产积累、作品公开观看和合格知识探索，保证设计目标与已实现能力之间的差异可审阅、可测试、可补足。

实际设计由三类执行边界组成：历史知识生产（D00—D05、独立 G、L0—L5）、Agent/工具与产品任务运行（研究、编辑、导演、发布组织）、用户体验消费（Studio、WATCH、EXP、Admin/Home）。这些边界可以共享代码与服务但不能共享未经隔离的权限、资格状态或真相写入权。优先复用当前仓库 `apps/web`、`packages/experience-engine`、`packages/data-access`、`skills/`、`pipelines/` 与已有 `supabase/migrations` 中经 M0 实际核验的能力；只有冲突与不足得到证实时才引入新的物理结构。

## 2｜软件模块与接口职责

**现有服务的具体复用边界（EG-11/17/18—23）：** Studio 研究/作品、出版服务、WATCH公开读取、EXP会话与追问、运营/Reviewer等接口已经实现了部分业务链路；既有数据读写包含psql与node-pg两后端。下游详细系统架构（SAD）及API契约必须从真实实现和U07需求同时推导，不得把已建接口写成全新建设项；也不得因存在 API 而宣布五图完整体验已通过。

- **入口与公开目录**：按角色提供可访问的 HOME、公开作品、Studio 工作空间、WATCH/EXP 合格消费与 Admin 工作面；不得允许浏览器伪造角色越过服务端权限。
- **受托任务与 Agent 运行**：负责调用计划、工具执行、预算、回执、研究候选/生产请求、可恢复状态与失效处理；Agent 只能调用受授权的生产 Tool/现有执行责任方，模型不得直接修改生产真相或 DOM。
- **专业生产引擎**：维持 D00—D05 单一生产主线及阶段所有权；Adapter 只提交候选与证据，Gate 由独立身份审查；不得另建与正式生产链竞争的 Studio 专用“快速真相”写入链。
- **公众知识消费门面**：WATCH/EXP 等公开消费者必须通过匹配版本、G5及上游资格、权利、用途/范围/consumer/有效时点的统一 Guard；不允许另一 API 或静态 JSON 绕过它。
- **受控项目研究读取门面（R1 POL-01）**：Studio 经有效项目授权可以持续查询合法 L0—L4 研究资产、原始资料和适当 L5 分面，不必对每一笔合法研究查询单独人工审批；此路径必须有来源权利/项目/用途控制、敏感限制、标签及审计，并且与公众公开消费 API/缓存隔离。**内研读权限不能写 Truth、不能绕过独立 Gate、不能用作公众展示许可。**
- **作品编辑与发布服务**：管理不可变 WorkRevision、导演节目单、差异/回退、投稿、运营审核、发行指针、撤回及重试幂等；作品发布与 G 资格是不同事务/策略条件。
- **WATCH/EXP 运行**：WATCH 的作品节目时码与历史时间分别实现；EXP 的独立会话状态与 WATCH 回跳起源分别存储；前台不得对外声称未知的空间几何精度。
- **运营与审计**：Admin 仅暴露有权信息；统计来自真实事件/持久化记录而非 UI 演示常量，权限操作留痕。

具体 API 路径、数据库表、事件字段和程序调用栈，以 K3 结合 U07 V4 的 85 候选 API、现有代码和 schema 合同形成唯一技术规范；这些**候选数量不证明对应接口当前存在**。

## 3｜数据、状态与修订的一致性

**历史生产终态差异（EG-06）：** `pipelines/data-production/run.mjs` 存在异常容忍式进度/终态处理路径，历史Stage/生产结果和审计写入失败必须被精确区分。后续状态机契约须定义业务终态、持久化审计终态、重试/回滚、幂等及不误报成功的负例，不能只靠现有 `completed` 字段宣布一致。

技术层保存并执行第三层规定的对象身份、修订版本、依赖、权限和资格条件，但不另造“什么是可信事实”的解释。研究工作候选、知识资产、作品修订、运营公开指针、体验会话和实际任务状态必须有独立的存储/转换边界。

至少保证：读写 Owner 清晰、合法输入/输出明示、不可变成果修订与可重放来源定位、并发修改有冲突控制、相同提交请求不会生成双发布、涉及资格与发行的事务有失败隔离、失权能向缓存和读取路径即时传达。不得因前台需要一键出版就允许 Agent/Operator 改写上游知识资格。

新 L1 读取单元、L5 六类派生及 L6 体验状态的真实物理存在或适配方式必须在 M0 阅读实际 SQL/代码后确认；旧逻辑层号不自动变更表名。新物理表必须论证必要性、所有者、约束、索引、访问权限、数据迁移、回滚和兼容性。已有 Schema 和 GATE 审计不能因 UI 升级被整体清空。

**KAD1｜资产/研究读/作品的最小物理合同。** 实现层须按KAD1下位统一合同§2/§5/§11/§12逐接口提供版本号/sha256、项目与角色ACL、权利与用途、幂等/CAS、稳定持久化与备份恢复。`StudioResearchRead`为项目内按L层最小授权读取，不能复用公众L5接口扩大L0—L4权限；13资产语义不得等同图片`public.assets`或可能级联删除的临时research_run。真实DDL/查询/DB RLS以本层授权技术细则为唯一实现Owner。

## 4｜统一合法消费与失效守卫

**既有消费者实现（EG-09/10）：** 已有六类L5派生消费与 `agent`、`visual_stage` consumer查询，实现能力需继续复用；但审计宽查询、缓存与未过期的旧 PASS 不得成为公众绕过当前权利和依赖闭包的路径。内部 Studio POL-01 研究接口与公开 G5 消费必须分开建立和测试授权。

**公众正式合格读服务**须在读取当时确认对象修订、当前适用 G5 决定、上游资格与权利、用途映射、scope、consumer、有效时点、依赖快照、版权动作和失效事件。Agent 和舞台可以消费不同分面；只读返回不得被误作具备写权限。

**内部 Studio 研究读取服务**单独按 R1 `POL-01` 校验项目授权、使用身份、L 层／资料来源、权利/敏感性、读取用途、可见性与审计，**不强制其先获得公众 G5**；必须返回认识和用途标签、不得让候选直接成为正式事实、不能被公开终端复用其内部缓存。对无权原件、跨项目数据和公开媒介权限须分别拒绝。

读取未授权或过期对象必须失败关闭；旧版本 PASS、过期缓存、Demo JSON、组件内 fallback 或不同公开 API 都不能绕过统一守卫。撤权先强制阻断受影响消费者，再在后台沿依赖更新索引、重审请求、审计和相应已公开作品/探索内容；对仍合法分面保持有证据的可用性。若影响范围不明则保守阻断不明部分，绝不能凭“缓存还在”复活撤权。

P08 控制事件、Gate 审计与发布回滚属于不同责任；控制请求不得自动伪造已被 Gate 审核的 REVOKED 记录，也不应待新 G5 PASS 才停止非法消费。

## 5｜身份、角色、ACL/RLS 与隐私

**当前安全实现及其不足（EG-24/28）：** Web端登录/资源归属守卫已有源码，不能认为系统尚无授权机制；但没有证据证明所有相关数据库表均受最小权限/Row Level Security保护。`SEC-01`仍是实际阻断，不得靠Web端登录或新增 `owner_user_id` 字段而销项。

权限以用户身份、项目、资产、操作、当前授权与使用情景共同判定，且强制发生于服务端/数据库边界，不能信任前端传入的角色或稿件所有者。Creator 编辑自己的工作成果并在项目授权内持续研究读取，Operator 根据明确授权审阅/出版，独立 Gate Reviewer 仅对知识资格签发；工程工具按 Owner 授权执行迁移/运维；公众只能读取合法公开资产。R1 `POL-02` 作品高风险复核不能用普通运营批准代替；`POL-04` 同一人兼任角色也要在请求时记录活动上下文、项目、动作与审计，不能凭 Owner 身份绕过调用边界。

数据库 RLS/GRANT/服务账号/密钥按最小权限原则设计，并用匿名、普通登录用户、不同所有者、运营和审核者的正反测试验证。不可把“有 owner_user_id 列”误认为已有 RLS，或把匿名用户的可访问性留给前端隐藏按钮来决定。

**当前现实安全阻断 SEC-01**：K0-G 对 `public.imported_materials` 的只读快照显示未启用 RLS，且 `anon`、`authenticated` 均拥有 SELECT/INSERT/UPDATE 权限，当时表为 0 行。这是须由实际有权工程/安全责任人在授权窗口重新核实、整改和攻防测试的风险；**不能在工程暂停期直接运行生产 SQL，也不能宣布问题已不存在**。策略设计必须先查真实调用与 Data API 暴露，避免仅启用 RLS 使合法业务全部中断。

**KAD1｜用户导入权利不可信与外部执行隔离。** 用户上传/AI导入若缺少可核实的license、授权主体、用途、条款和有效期，应默认`unknown/restricted`，不得由前端自动设置`rights_clear=clear`；素材读取权不等于再发布/修改/导出许可。`SEC-01`与所有数据API、GRANT、RLS、project/role ACL和跨用户负例必须留在授权工程验收，不能被设计修订标为安全PASS。

## 6｜跨代际合同与机器路由迁移

**既有Skill/Registry激活差异（EG-07/08/31）：** 六阶段 Executor与 `skills/README_DATA_PRODUCTION_SKILLS.md` 仅列五个活动 Stage Owner 不一致；生产 Registry 的目标文档声明、全局 `enabled`、Job级状态、Reviewer绑定属于不同版本/证据层。明确运行版本和实际读取方后再做兼容，未获得工程恢复授权不得修改活跃Registry或为消除表面差异自动改Skill ID。

K3 需一次性定义最终应用与退出的合同清单，至少包括：

- `AGENTS.md` 唯一新权威版本路由；`CURRENT.md` 实际当前状态；`OWNERSHIP_MAP.md` 工程目录责任；三者不可复制最高规则全文。
- 原 C0—C4 的完整历史身份及 `REVIEW_DRAFT_NOT_APPLIED` 证据，目标 MHKA 的设计有效性和真实工程激活证据。
- `specs/FOUNDATION.md` 旧“三层”不与新五层作为最高架构竞争；可降为历史或无规范性导航。
- `DATA_CONTRACT.md` 与目标六阶段 L/G 语义保持一致；`AGENT_CONTRACT.md` 旧 `L4 Trusted Read Model` 必须显式映射到当前受权 L5 的 Agent 分面，`EXPERIENCE_CONTRACT.md` 旧 `L5 Experience Runtime` 必须与新 L6 Runtime 分开，不能仅替换数字。
- `MoHen_Data_Production_Protocol.md`、`production-registry.json`、方法绑定、Machine Gate、持久化绑定、Guard、Schema、测试计划必须在同一架构代际上互相对得上。
- 旧 Developer/Agent Skill 的 Registry/Skill卡片/Stage Owner/Executor/Agent调用入口不得通过 MHKA-04 新标签直接批量改名；依 R1 `POL-03` 与 R3 的 `CTX-ENG/CTX-PROD/CTX-STUDIO/CTX-EXPLORE` **现行四类执行上下文**（历史 `ENG/PROD/EXPLORE/BASE` 仅作为需逐条核验的候选旧标签）建立兼容映射，保留现有六生产阶段/方法/审核身份。任何 Agent 调度现有生产能力都必须通过有权限的 Production Tool，而非把 `production-registry` 标成 Agent 可写即算实现。

Registry 的 `activation.enabled=true`、合同 `DESIGN_TARGET_NOT_APPLIED`、代码中存在 API、数据库表存在和真实 Gate 发出签名是**不同证据**。迁移过程中应逐项验证真实代码读取者和引用者，禁止把目标 JSON 标记当实际系统切换完成。

## 7｜独立 Gate 的投运与系统权限守卫

**需要改造而不是重建的已知冲突（EG-03/05/21）：** Stage Executor的 `disposition=PASS` 只能表明生产阶段流转；Adapter现有 `gate_audits` 写路径不得被当成独立资格服务。后续必须证明Producer与Reviewer代码进程、数据库账号/写权限、角色和失败拒绝均真实隔离；已有运营作品Reviewer不能替代六门。工程整改只在授权期施工。

Gate Producer/Reviewer 的进程身份、数据库角色、签发策略版本、机审白名单、风险升档、人工复核与撤权审计必须有实际配置和可复核测试。Producer 可提交候选、来源与缺口，不允许替 Reviewer 写资格决定；Operator 的作品审批不允许绕过独立 G。只有当真实 `E1-GATE-ACTIVATE` 授权及写/读/撤权安全回归满足，相关 Gate 及消费服务才可按特定范围启用。

设计期 `U04 DESIGN_CONTRACT_CLOSED` 证明六类技术规则设计有界完成，不证明运行身份已经激活。没有 Owner 的 M0/E1 独立授权，不改变数据库、服务身份、真实签名和公网上线状态。

**KAD1｜独立G Gate实码守卫。** Producer/Adapter/外部AI/Operator/Owner产品选择都不能伪造专业签发；实际签发须独立具名Reviewer与有权策略版本，原数据库事件不可变、目的/消费者/范围/修订当前有效，并有负例和回滚。当前若只有迁移DDL、隔离测试或目标政策，而无真实Reviewer启用，须保持`E1-GATE-ACTIVATE=HOLD`，不得以PASS宣称新资格投运。

## 8｜前端消费与可感知的工程质量

Studio 必须让受托研究/编导/草稿/改稿/保存的状态逐步可见，不能靠 mock 文本循环掩盖真实模型/工具未完成；WATCH 的页面、播放器和证据展示应忠于发布的作品修订；EXP 的自然语言问询、视觉舞台和关系/时空表达只能以合格知识与允许的假设方式呈现；Admin 的审核、发布、统计和权限必须连接真实受保护的数据状态。

分设备 UI 交互应遵守 02 的模式壳和响应式规则；从视觉草图到真实代码的差异必须列在工程验收账。原 19 组件可按复用分析适配，27 类共享组件及 85 API 是候选工程设计；不需要机械地与数量逐一相同，关键是 62 模块和 152 行为是否具备实际服务/错误结果。

## 9｜测试、验收、观测与故障复原

**真实已有与未验证的分账（EG-12/25/26/30）：** 2026-10-18金泽样板闭环、2026-10-29项目报告中的140测试、40条API金线及Vercel READY是可继承的特定时点运行证据；它们必须转成有提交/环境的回归测试种子，不能取代`CURRENT.md`当时记载的五图152条用户动作 `0 PASS/151 NOT_RUN/1 UNVERIFIED`，也不能证明当前数据库安全/独立Gate已通过。

测试分五个相互不能替代的层次：静态规范/类型与协议一致性；权限、资格和反例单元测试；受托研究/创作/发布/消费的真实集成与端到端测试；跨设备人文体验实测；部署环境和数据库安全/恢复的运行证据。所有 `PASS` 指向具体提交、环境、用例、输入输出、身份、证据时间，不给“全部已验”抽象标签。

U07 V4 的 442 条基线与 75 条新增设计用例、41 条跨体系断言提供完整测试要求，**目前在 K1 只做静态继承和 SHA 校验，没有一条由此获得真实 E1 PASS**。应覆盖非预设题目研究、未找到材料、外部工具失效、越权访问他人草稿、改稿并发、重复发布、失效撤权、旧缓存阻断、历史地图无精确几何、WATCH→EXP/返回、无图像许可的合法降级与低覆盖 EXP。

有失败必须保存具体请求/对象引用、阶段、原因和最小复原动作；不可因异常将部分成功的合格分面清空，也不可让旧授权失效后继续显示历史缓存。成本与外部模型调用记录不得写入明文凭据或暴露用户隐私。
