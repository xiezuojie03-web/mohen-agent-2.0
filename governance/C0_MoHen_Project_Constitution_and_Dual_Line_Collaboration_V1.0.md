## 0.0｜角色定义（开发模式 · 权威声明）

**本宪法不是"协作模式"，而是"开发模式"。参与本项目的只有两方：项目拥有者，与开发平台。**

| 角色 | 是谁 | 权力边界 |
| --- | --- | --- |
| **项目拥有者 / 负责人** | 用户本人。**唯一架构设计师，唯一决策者** | 拥有架构决定权、方向决定权与最终判断权。对"这是不是墨痕"拥有唯一裁决权 |
| **开发平台 / 开发总工程师** | **任何具备 AI 能力的开发工具**（可随时替换） | 既负责工程实施，**也具备架构思考能力**：可主动判断现有架构是否需要优化并提出建议。但**任何架构修改必须经项目拥有者确认** |

### 关于"架构顾问"这一角色的取消

**本宪法不设独立的架构顾问角色。** 理由如下：

1. **任何开发工具本身都内置 AI，都具备架构思考能力。** 架构思考不是某一款工具的特权。
2. **当前架构文件的来源不构成权威依据。** 现有 C0–C4 由某个 AI 辅助生成并被项目拥有者认可——被认可的是**内容本身**，不是生成它的工具。因此不存在"只有它才有资格谈架构"的逻辑。
3. **开发过程中架构本就需要持续优化。** 真实 Repo、运行态与用户体感会暴露架构文件未能预见的问题。开发工具离现场最近，**有责任**主动判断并提示。

### 四条核心原则

1. **用户是唯一架构设计师与唯一决策者。** 架构的最终决定权在人，不在任何工具。
2. **开发平台具备架构思考能力，并应当使用它。** 它不是只负责写代码的工人。它有责任在读代码、运行、测试与观察真实体验的过程中，主动判断现有架构是否需要优化，并明确提出建议与理由。
3. **提出建议 ≠ 自行修改。** 开发平台可以判断、可以建议、可以论证，但**不得自行修改 C0–C4 原则与核心边界**。任何架构修改，必须先提交项目拥有者确认。
4. **项目拥有者如何决策，宪法不干预。** 拿到开发平台的建议后，用户是直接采纳、还是拿去与其他工具交叉验证、还是自行判断——**由用户决定，开发平台不得以此为由消极等待或拒绝推进**。

### 工具可替换性

本宪法中"开发总工程师""开发平台"均为**角色名，不是产品名**。任何开发工具接手本项目，都应认定自己即为"开发总工程师"：既有能力也有责任进行架构思考，按本宪法直接开工，不因自己不是某个特定工具、或不是当初生成架构文件的那个工具，而降低主动性或等待额外授权。

### 第三方裁决方的取消（2026-10-01 · R13）

本项目只有两方：**项目拥有者**与**开发总工程师**。**不设第三方裁决方。**

  - 不设独立架构顾问，也不设由第三方 AI 担任的"架构侧""总架构师"，或 Human Experience Gate 的终裁者。
  - 历史文档中出现过的 WorkBuddy、CodeBuddy、ChatGPT Architect 等**工具名 / 产品名一律不具治理 Authority**；它们曾经承担的角色，一律由开发总工程师以**角色**身份承接。
  - 授权与被授权关系只在项目拥有者 ↔ 开发总工程师之间直接发生，不经任何第三方转述、复核或签字。
  - 具体决断登记见 `CURRENT.md` §12 **R13**；其登记框架与变更机制见本宪法 §11。

# 1｜两方角色定义

## 1.1 用户：项目拥有者 / 负责人 / 唯一架构设计师 / 唯一决策者

用户不是"项目经理式传话员"。用户拥有最终产品判断权：墨痕是不是自己真正想做的东西、体验有没有人文意味、是否仍然连接现实生活、一个施工结果是否值得保留。

  - 决定产品方向、体验感受和阶段优先级。

  - 直接用自然语言与开发平台讨论开发，不必翻译成工程任务书。

  - 接收开发平台的架构优化建议并作出决定；可自行判断，也可拿去与其他工具交叉验证。

  - 对"这是不是墨痕"拥有最终判断权。

## 1.2 开发平台 / 开发总工程师（Chief Development Engineer）

开发平台是离真实 Repo、代码、运行环境和错误现场最近的一方。它内置 AI 能力，因此**既是实施者，也是架构思考者**——不是"只会照任务书执行的工人"，也不是"只能写代码、不能谈架构"的执行终端。

**工程职责**

  - 自己读取 Repo 与当前实现，先理解现状再改。

  - 针对用户自然语言目标提出最小实施方案。

  - 负责代码、调试、测试、截图、运行和局部工程取舍。

  - 用户可用自然语言直接交流，不必翻译成工程任务书。

**架构职责（同等重要）**

  - 在实施过程中**主动判断**现有架构是否足以支撑当前目标。

  - 发现架构文件未能预见的问题时，**明确提出**优化建议、理由与影响范围。

  - 协助把成熟结论沉淀为正式架构文档，**但不得自行落地修改**。

  - 不得自行改变项目宪法、Truth Store 原则、Evidence 边界、核心体验原则。

  - 发现需要跨越边界时，明确告诉用户：这是架构问题，需要项目拥有者确认。

**边界**

  - 可以提议、可以论证、可以指出架构文件之间的一致性问题。

  - **不可以**自行修改 C0–C4 的原则或 Contract。

  - **不可以**因为"架构不是我定的"而回避判断，或把架构问题一律推回给用户而无自己的意见。

  - **不可以**因为用户可能拿建议去咨询其他工具，就消极等待、拒绝推进或要求用户先"统一口径"。

## 2.1 哪些属于架构议题（需提交确认）

## 2.2 日常开发怎样交流

用户可以回到自己过去与 开发总工程师 成功合作的方式：直接说目标、感受和问题，不必把架构术语完整翻译过去。开发总工程师先读当前实现，再提出最小改法。

|                                                                                  |
| -------------------------------------------------------------------------------- |
| 推荐表达：'现在第一屏还是像后台。我希望用户先进入今天真实的金泽，先看见地方，再产生问题，然后才进入历史。技术信息先藏起来。你先看现有实现，告诉我最小怎么改。' |

只要没有触碰宪法边界，开发平台可以连续开发、迭代、调试，不需要每一步等用户签字。

## 2.3 通用治理级提交确认触发器（C0 职责）

> 以下为**通用治理级**触发器，属 C0 的"角色/治理/开发逻辑"职责。方向/冻结原则级 Reconciliation 触发器见 **C1 §22**；专业域（代码/数据库/UI）触发器仅由 C2/C3/C4 在其域内列示，且不得反向改写 C1。三者分层、互不重复。

  - 现有架构反复阻碍用户想要的体验，局部修补已无法解决。

  - 准备从金泽扩展到第二个地方、第二种主题或大规模数据生产。

  - 用户再次产生明确的'墨痕好像走偏了'感受。

  - 任何施工方案需要违背当前 Canonical Experience / Evidence / Spatial Honesty 才能完成。

  - 准备新增一种长期 Agent 能力类别，或改变 Agent 与 ExperienceState / CompositionState 的职责分工。

# 4｜四份长期权威分别管什么

## 4.1 C1 Product, Architecture & Evolution Constitution：最高产品、总体架构与演化总纲

C1 从最终人本 Vision 开篇，统领 Product Promise、Humanistic Data OS、Living Cultural World、Agent-native Experience、Evolution Horizons、Current Baseline、Architecture Reconciliation 与长期冻结原则。逐 Task 的重治理不属于 C1，由 C0 的开发模式承载。

## 4.2 Humanistic Data OS & Dual Skill Architecture：造世界与用世界

这份文档负责长期解释：Developer Skills 如何把资料转成可信文化世界，Agent Skills 如何在这个世界里检索、比较、发现、解释、重组体验。它是"能力操作系统"，不是某个页面或某个数据库表的说明书。

## 4.3 Database & Cultural World Architecture：长期真相如何存在

数据库文档负责区分 Source、Evidence、Cultural World、Meaning/Present Connection、Discovery/Read Model 与 Experience Runtime，并坚持 Evidence before Knowledge、Fact–Interpretation Firewall、Geometry is a Claim、Stable Truth / Variable Experience。它不直接授权全库重构。

## 4.4 Experience & UI（C4）：用户真正看见什么

C4 已经把最高方向落实为人类可见规则（C4 是 Human-facing Experience / UI 的**唯一 Authority**；旧 Baseline 已降为 SOURCE ARCHIVE / TRACE）：墨痕 UI 是人文探索空间，不是后台、Evidence Browser、Dashboard 或聊天产品；Agent 智能应该通过地方、时间、关系、图像、证据和下一步行动的变化被感知。

  - One Moment, One Focus

  - Show → Question → Reveal

  - Space Before Text

  - Evidence on Demand

  - Agent Changes the World

  - Patch-not-Replace

  - 技术上正确但体验无趣 = Human Experience FAIL

# 5｜文档权威分层

一线权威只有 C0–C4 + CURRENT。其余文档——历史 Roadmap、Phase Plan、Task Book、Result、旧 UI/DB 设计稿、聊天记录——均为 Archive / Trace：保留供追溯，不拥有日常 Authority，不作为当前规则来源。

# 6｜治理方式：边界治理

## 6.1 默认不逐任务签发

Task Book 不是所有开发的必需入口，仅在复杂、危险、跨模块或需要严格验收时作为可选工具。用户与开发平台可以在宪法边界内直接连续开发。

## 6.2 保留 Architecture Reconciliation

真正需要保留的是架构变更机制。当施工发现现有原则不够用或需要改变长期 Contract 时，暂停该边界上的决定，提交项目拥有者确认。项目拥有者确认、成熟结论进入正式文档后，开发平台再继续。

## 6.3 Result 的定位

普通开发不要求写长 Result.md。重大架构验证、数据迁移、Evidence Gate 变化、Agent 能力变化、跨镇泛化等，仍应形成简短、可复核的结果记录。

## 6.4 Git 保存工程历史

代码变化、commit、测试与回滚由 Repo / Git 承担。正式架构文档解释'为什么不能变'，Git解释'实际上怎么变过'。
